## 一、问题概述

V4.3任务生成引擎的"每目标24小时最多2个任务"频率限制机制存在于设计文档和查询脚本中，但未集成到实际的任务生成执行路径。测试发现过去24小时内7个目标共生成71个任务，远超14个的理论上限。

## 二、核心优化方案

### 方案1: 在AutoTaskGeneratorV43中集成频率限制（推荐）

**目标文件**: `sds/auto_task_generator_v43.py`

在`create_tasks_from_recommendations`方法中，创建任务前增加频率检查：

```python
def check_goal_frequency(self, goal_code: str, max_tasks: int = 2, window_hours: int = 24) -> tuple:
    """
    检查目标在过去N小时内的自动生成任务数
    返回: (allowed: bool, current_count: int, remaining: int)
    """
    sql = """
        SELECT COUNT(*) as count
        FROM tasks
        WHERE task_type LIKE 'auto_generated_v4%'
          AND created_at >= NOW() - INTERVAL %s HOUR
          AND title LIKE %s
    """
    results = execute_query(sql, (window_hours, f'{goal_code}: %'))
    count = results[0]['count'] if results else 0
    allowed = count < max_tasks
    return allowed, count, max(0, max_tasks - count)

def create_tasks_from_recommendations(self, recommendations: List[Dict]) -> List[int]:
    """带频率限制的批量任务创建"""
    import re
    
    # 按目标分组
    goal_counts = {}  # 运行时计数
    
    created_ids = []
    skipped_freq = []
    skipped_dup = []
    
    for rec in recommendations:
        title = rec.get('title', '')
        
        # Step 0: 提取目标前缀
        match = re.match(r'(T\d+)', title)
        if not match:
            goal_code = 'UNKNOWN'
        else:
            goal_code = match.group(1)
        
        # Step 1: 频率限制检查
        allowed, count, remaining = self.check_goal_frequency(goal_code)
        # 加上本轮已创建的数量
        runtime_count = goal_counts.get(goal_code, 0)
        if count + runtime_count >= 2:
            skipped_freq.append({
                'title': title,
                'goal': goal_code,
                'reason': f'频率限制: 24h内已有{count + runtime_count}个任务'
            })
            continue
        
        # Step 2: 去重检查（原有逻辑）
        # ... 保持现有filter_duplicate_tasks逻辑 ...
        
        # Step 3: 质量检查（原有逻辑）
        # ... 保持现有quality_filter_tasks逻辑 ...
        
        # Step 4: 创建任务
        task_id = self.create_task(rec)
        if task_id:
            created_ids.append(task_id)
            goal_counts[goal_code] = goal_counts.get(goal_code, 0) + 1
    
    # 日志输出
    logger.info(f"频率限制: 跳过了 {len(skipped_freq)} 个任务")
    for skip in skipped_freq:
        logger.info(f"  跳过: {skip['title'][:50]} ({skip['reason']})")
    
    return created_ids
```

**优点**:
- 最小改动，直接在生产代码中生效
- 支持运行时计数（同一批次内也不会超标）
- 保留现有去重和质量检查逻辑

### 方案2: 使用数据库触发器（备选）

在数据库层面添加插入前触发器，强制检查频率：

```sql
DELIMITER //
CREATE TRIGGER before_task_insert
BEFORE INSERT ON tasks
FOR EACH ROW
BEGIN
    IF NEW.task_type LIKE 'auto_generated_v4%' THEN
        DECLARE goal_prefix VARCHAR(10);
        DECLARE task_count INT;
        
        -- 提取目标前缀 (简化版，仅支持T1-T9)
        SET goal_prefix = SUBSTRING(NEW.title, 1, 2);
        
        SELECT COUNT(*) INTO task_count
        FROM tasks
        WHERE task_type LIKE 'auto_generated_v4%'
          AND created_at >= NOW() - INTERVAL 24 HOUR
          AND title LIKE CONCAT(goal_prefix, '%');
        
        IF task_count >= 2 THEN
            SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = '频率限制: 该目标24小时内已生成2个任务';
        END IF;
    END IF;
END//
DELIMITER ;
```

**优点**: 数据库层面强制执行，绕过应用层也无法违规
**缺点**: 触发器维护成本高，错误处理不友好

### 方案3: 独立的频率限制中间件（长期方案）

创建一个独立的`FrequencyLimiter`类，作为所有任务生成路径的统一入口：

```python
class FrequencyLimiter:
    """统一的频率限制中间件"""
    
    def __init__(self, db_connection, config=None):
        self.config = config or {
            'max_per_goal_24h': 2,
            'max_total_24h': 20,  # 全局上限
            'window_hours': 24
        }
    
    def check_and_acquire(self, goal_code: str) -> bool:
        """检查并获取生成许可"""
        # 1. 检查目标级别限制
        goal_ok = self._check_goal_limit(goal_code)
        # 2. 检查全局级别限制
        total_ok = self._check_total_limit()
        # 3. 记录使用量（防并发）
        if goal_ok and total_ok:
            self._record_usage(goal_code)
        return goal_ok and total_ok
```

## 三、积压任务处理建议

当前38个pending任务需要分类处理：

### 3.1 清理策略

```sql
-- 查看每个目标的pending任务数
SELECT 
    SUBSTRING(title, 1, 2) as goal,
    COUNT(*) as pending_count,
    GROUP_CONCAT(id ORDER BY id) as task_ids
FROM tasks
WHERE task_type = 'auto_generated_v4.3'
  AND status = 'pending'
  AND created_at >= NOW() - INTERVAL 24 HOUR
GROUP BY goal
ORDER BY pending_count DESC;
```

### 3.2 建议操作

1. **保留每个目标最新的2个pending任务**，其余标记为`redundant`：
   - 避免有价值的任务被误删
   - 释放调度器压力
   - 保持可追溯性

2. **标记时写入notes说明**：
   ```sql
   UPDATE tasks
   SET status = 'redundant',
       notes = CONCAT('频率限制清理: 该目标24h内任务数超标，保留最新2个任务'),
       updated_at = NOW()
   WHERE id IN (需要清理的任务ID列表);
   ```

## 四、数据结构优化建议

### 4.1 goal_id字段填充

当前所有自动任务的`goal_id`为NULL，建议：

1. **在插入时自动填充**: 从标题解析目标前缀后，查询goals表获取对应id
2. **或者添加goal_code字段**: 在tasks表中增加`goal_code VARCHAR(10)`字段，直接存储T1-T7

```sql
ALTER TABLE tasks ADD COLUMN goal_code VARCHAR(10) NULL;
CREATE INDEX idx_goal_code ON tasks(goal_code);
```

## 七、风险与注意事项

1. **清理积压任务可能误删有用任务** → 采用标记(redundant)而非删除，保留恢复可能
2. **频率限制可能影响紧急任务生成** → 预留"紧急通道"机制（特殊优先级可绕过限制）
3. **标题格式不规范可能导致目标解析失败** → 需要规范化任务标题生成逻辑
4. **并发生成场景下的竞态条件** → 使用数据库行锁或原子操作防止超限
