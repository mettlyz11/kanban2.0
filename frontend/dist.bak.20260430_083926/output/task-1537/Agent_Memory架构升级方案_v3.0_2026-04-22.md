## 🎯 升级背景与目标

### 当前现状
- **v2.0 Markdown-based Memory：** 文件系统存储，目录结构分层
- **规模：** 12+ 记忆文件，~50KB 总大小
- **检索方式：** `memory_search` 语义搜索 + 文件路径硬编码读取
- **问题：** 跨session深度回忆能力有限，缺少关联推理能力

### MCP 2026预测
Memory正在成为Agent系统的first-class primitive，结构化Graph Memory是行业标准方向。

### 升级目标
1. ✅ **结构升级：** Markdown文件 → 混合存储(Markdown + Graph)
2. ✅ **能力升级：** 关键词匹配 → 语义关联推理
3. ✅ **性能升级：** 文件扫描 → 图索引毫秒级检索
4. ✅ **可观测性：** 黑盒状态 → 全链路可监控

## 🧠 一、Knowledge Graph 设计

### 1.1 核心实体类型 (9类)

| 实体类型 | 前缀 | 说明 | 当前数量 |
|---------|------|------|---------|
| 概念 (Concept) | C: | 核心概念、方法论、原则 | 30 |
| 任务 (Task) | T: | 看板任务、执行记录 | - |
| 文档 (Document) | D: | Markdown文件、产出物 | - |
| 人 (Person) | P: | 联系人、用户画像 | 48+ |
| 项目 (Project) | Prj: | 进行中项目 | 7 |
| 工具 (Tool) | Tool: | 技能、脚本、API | 20+ |
| 事件 (Event) | E: | 重要时间节点 | - |
| 洞察 (Insight) | I: | 研究发现、结论 | - |
| 能力 (Capability) | Cap: | Agent能力注册 | 4 |

### 1.2 核心关系类型 (12类)

| 关系类型 | 反向关系 | 说明 |
|---------|---------|------|
| `引用 (REFERENCES)` | `被引用` | 文档→概念，任务→文档 |
| `包含 (CONTAINS)` | `属于` | 目录→文件，项目→任务 |
| `相关 (RELATED_TO)` | `相关` | 概念↔概念，任务↔任务 |
| `执行 (EXECUTES)` | `被执行` | 任务→工具，Agent→任务 |
| `产生 (PRODUCES)` | `来源于` | 任务→文档，Research→洞察 |
| `触发 (TRIGGERS)` | `被触发` | 事件→任务，任务→后续任务 |
| `分配 (ASSIGNED_TO)` | `负责` | 任务→人，项目→人 |
| `使用 (USES)` | `被使用` | 任务→模型，工具→API |
| `优先级 (PRIORITIZES)` | `被优先` | 战略→项目，目标→任务 |
| `时间 (OCCURS_AT)` | - | 事件→日期，任务→截止日 |
| `继承 (SUBCLASS_OF)` | `父类` | 概念层级 |
| `同义词 (SYNONYM_OF)` | `同义词` | 术语统一映射 |

### 1.3 关系属性权重

每条关系边包含：
- `strength` (0.0-1.0): 关联强度
- `confidence` (0.0-1.0): 置信度
- `created_at`: 创建时间
- `last_accessed`: 最后访问时间
- `access_count`: 访问计数（用于加权）

**权重衰减机制：**
```
每日衰减系数 = 0.99  (1%/天)
使用加权系数 = 1.0 + (access_count × 0.01)
实际权重 = base_strength × decay_factor × usage_factor
```

## 🔍 二、混合检索管道

### 2.1 三阶段检索流程

```
用户Query
    ↓
[Phase 1: 向量粗筛]
    ├─ Query → Embedding
    ├─ Faiss ANN 搜索 (Top 50)
    └─ 候选节点集合
    ↓
[Phase 2: 图路径扩展]
    ├─ 对每个候选节点做1-2跳邻居扩展
    ├─ 路径评分: 节点权重 + 边权重 + 路径长度惩罚
    └─ 扩展节点集合 (Top 30)
    ↓
[Phase 3: 语义重排序]
    ├─ 计算Query与每个节点的语义相似度
    ├─ 结合图结构重要度 (PageRank)
    └─ 最终排序结果 (Top 10)
    ↓
上下文注入
```

### 2.2 检索评分公式

```
最终得分 = (0.4 × 语义相似度) 
         + (0.3 × 图结构重要度) 
         + (0.2 × 时间衰减因子) 
         + (0.1 × 使用频次权重)
```

### 2.3 检索接口

```python
# 语义搜索（兼容v2.0）
memory_search(query, top_k=10, domain=None)

# 图遍历（新增v3.0）
graph_traverse(start_node, hops=2, relation_filter=None)

# 混合查询（v3.0推荐）
hybrid_query(query, graph_weight=0.3, vector_weight=0.7)
```

## 📁 三、存储层设计

### 3.1 持久化方案

**双写机制（写时复制）：**
```
写入操作
    ↓
┌─ 写入 Markdown 文件 (Source of Truth)
│   - 人类可读
│   - Git版本控制
│   - 最终权威
│
└─ 异步更新 Graph + Vector 索引
    - 索引加速
    - 可重建
    - 最终一致
```

**文件布局：**
```
memory/
├── graph/
│   ├── concepts.jsonl      # 概念节点
│   ├── relations.jsonl     # 关系边
│   ├── entities.jsonl      # 实体节点
│   ├── rules.jsonl         # 行为规则
│   ├── capabilities.json   # Agent能力注册
│   ├── weights.json        # 衰减权重
│   └── index.json          # 元数据索引
│
├── embeddings/
│   ├── faiss_index.bin     # Faiss向量索引
│   └── id_mapping.json     # 向量ID映射
│
└── [领域文件保持不变]
    ├── core-principles.md
    ├── domains/
    ├── projects/
    └── daily/
```

### 3.2 一致性保障

**校验机制：**
1. **Graph ↔ Markdown 一致性校验**（每小时）
   - 统计Markdown中的[[wikilink]]
   - 与Graph边对比
   - 自动补全缺失关系

2. **Embedding 索引校验**（每日）
   - 检查所有节点都有向量
   - 验证维度一致性
   - 重建损坏索引

3. **损坏自动恢复**
   - Graph损坏 → 从Markdown重建
   - Embedding损坏 → 重新生成
   - Markdown损坏 → Git恢复
