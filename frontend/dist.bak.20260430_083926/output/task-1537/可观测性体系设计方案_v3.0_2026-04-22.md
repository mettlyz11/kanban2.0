## 📊 一、可观测性Dashboard设计

### 1.1 Dashboard视图结构

**主视图 - 全局概览 (5分钟刷新)**

| 指标卡片 | 内容 | 阈值告警 |
|---------|------|---------|
| 🟢 系统健康度 | 总体评分(0-100) | &lt;80 → 黄色, &lt;60 → 红色 |
| 💰 今日Token消耗 | 输入/输出/总成本 | &gt;50万 → 黄色, &gt;100万 → 红色 |
| 🤖 活跃Subagent | 运行中/排队/完成 | &gt;10 → 黄色, &gt;20 → 红色 |
| ❌ 错误率 | 近1小时错误率 | &gt;5% → 黄色, &gt;15% → 红色 |
| 🧠 Memory健康度 | 图谱完整度/检索命中 | &lt;70% → 黄色 |
| 📋 任务吞吐量 | 完成/新增/积压 | 积压&gt;20 → 黄色 |

**详细视图 - 分面板**

1. **Token成本分析面板**
   - 按模型维度消耗统计（饼图+趋势线）
   - 按任务类型消耗分布
   - 单位成本优化建议
   - 7天/30天成本预测

2. **Subagent生命周期追踪面板**
   - Subagent启动/完成时间线
   - 平均执行时长（按任务类型）
   - 成功率/失败模式分类
   - 并发度热力图

3. **Memory系统监控面板**
   - 概念节点增长趋势
   - 关系边密度变化
   - 检索命中率
   - 衰减曲线可视化
   - 索引健康度

4. **错误分析面板**
   - Top 10错误类型
   - 错误时间分布
   - 错误溯源链路
   - 自动恢复成功率

### 1.2 Dashboard技术实现

**技术栈选型：**
- **前端框架：** Streamlit（快速迭代）→ 迁移到React（长期）
- **图表库：** Plotly + Altair
- **数据后端：** SQLite (metrics.db) + Redis（实时数据缓存）
- **刷新机制：** 5分钟自动刷新 + 手动刷新按钮

**核心SQL表结构：**

```sql
-- token成本记录表
CREATE TABLE token_metrics (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp DATETIME DEFAULT CURRENT_TIMESTAMP,
    model_name VARCHAR(100),
    task_id INTEGER,
    task_type VARCHAR(50),
    input_tokens INTEGER,
    output_tokens INTEGER,
    total_cost DECIMAL(10,4),
    provider VARCHAR(50)
);

-- subagent追踪表
CREATE TABLE subagent_trace (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id VARCHAR(100) UNIQUE,
    task_id INTEGER,
    start_time DATETIME,
    end_time DATETIME,
    duration_seconds INTEGER,
    status VARCHAR(20),
    error_message TEXT,
    agent_type VARCHAR(50),
    memory_usage_mb INTEGER
);

-- 错误日志表
CREATE TABLE error_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp DATETIME,
    error_type VARCHAR(50),
    error_message TEXT,
    stack_trace TEXT,
    component VARCHAR(50),
    session_id VARCHAR(100),
    recovered BOOLEAN DEFAULT 0
);

-- memory健康度表
CREATE TABLE memory_health (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp DATETIME,
    total_concepts INTEGER,
    total_relations INTEGER,
    retrieval_hits INTEGER,
    retrieval_misses INTEGER,
    index_size_mb INTEGER,
    avg_similarity_score DECIMAL(5,4)
);
```

## 📈 二、成本监控与优化机制

### 2.1 成本监控体系

**三级成本阈值告警：**

| 级别 | 触发条件 | 通知方式 | 响应动作 |
|-----|---------|---------|---------|
| L1 警告 | 日消耗 > 50万token | CoCo消息 | 生成成本优化报告 |
| L2 告警 | 日消耗 > 100万token | CoCo + 邮件 | 自动降级非关键任务模型 |
| L3 紧急 | 日消耗 > 200万token | CoCo + 邮件 + 电话 | 暂停所有Research任务，人工介入 |

**成本预测模型：**
- 基于历史7天数据的ARIMA预测
- 按任务类型的成本归因
- 模型性价比评分动态调整

### 2.2 成本优化策略

**策略1：智能模型路由**
```
任务类型 → 推荐模型
────────────────────
代码任务    → huoshanCoding/ark-code-latest ($0.002/ktoken)
Research   → moonshot/kimi-k2.6 ($0.01/ktoken)
常规对话   → dmxapi/kimi-k2.5-free (免费)
摘要/分类  → deepseek/deepseek-chat ($0.007/ktoken)
```

**策略2：Token压缩技术**
- 上下文截断：保留最新10轮对话，历史摘要化
- Prompt优化：移除冗余描述，使用结构化格式
- 输出长度控制：按任务类型设置max_tokens上限

**策略3：缓存复用机制**
- 常用Query结果缓存（TTL 24小时）
- 嵌入向量缓存（SQLite + Faiss索引）
- 相同Research任务结果共享

### 2.3 成本分析报表

**日报内容：**
- 当日总消耗 vs 预算
- Top 5消耗任务
- 模型使用分布
- 成本异常检测
- 优化建议

**月报内容：**
- 月度成本趋势
- 任务ROI分析
- 模型性价比排名
- 下月预算建议

## 🔔 三、告警机制设计

### 3.1 告警分类与级别

| 告警类型 | L1 警告 | L2 告警 | L3 紧急 |
|---------|--------|--------|---------|
| **系统类** | 磁盘&gt;80%<br>内存&gt;85% | 磁盘&gt;90%<br>内存&gt;95%<br>网关异常重启 | 服务不可用<br>数据库连接失败 |
| **任务类** | 积压&gt;20<br>失败率&gt;5% | 积压&gt;50<br>失败率&gt;15% | 调度器死锁<br>任务无限循环 |
| **成本类** | 日耗&gt;50万token | 日耗&gt;100万token | 日耗&gt;200万token |
| **Memory类** | 检索命中&lt;70%<br>概念增长停滞 | 索引损坏<br>检索失败&gt;10% | Memory文件损坏<br>图谱不一致 |
| **Subagent类** | 超时&gt;30min<br>并发&gt;10 | 超时&gt;60min<br>并发&gt;20 | 僵尸进程&gt;5<br>内存泄漏 |

### 3.2 告警通知渠道

```
L1 警告 → CoCo消息 (#alerts频道)
L2 告警 → CoCo消息 + 邮件通知
L3 紧急 → CoCo消息 + 邮件 + 电话通知 (待接入)
```

### 3.3 告警自愈机制

**自动恢复流程：**
1. 检测到异常
2. 记录完整上下文
3. 执行预设恢复动作
4. 验证恢复效果
5. 生成事故报告

**已支持的自愈动作：**
- Gateway服务重启
- 清理僵尸Subagent进程
- Memory索引重建
- 数据库连接重置
- 模型自动降级
