# 实验室核心算法代码存证方案

> **依据**：2026版《商业秘密保护规定》第XX条（技术秘密证据保全条款）、《电子签名法》《人民法院在线诉讼规则》
> **目的**：为核心算法提供具有法律效力的权属证明和生成时间证明，构建完整证据链
> **适用范围**：A级核心算法、B级重要算法的关键版本
> **编制日期**：2026年4月25日

---

## 一、存证法律依据与证据效力

### 1.1 法规依据

2026版《商业秘密保护规定》强化了对技术类商业秘密的证据保全要求：

> **第XX条**：权利人可以通过时间戳、区块链存证、公证等方式固定商业秘密的内容、形成时间、权属关系等信息。
> **第XX条**：人民法院审查认定商业秘密时，应当综合考虑存证方式的可信度、存证时间的连续性、存证内容的完整性。

### 1.2 证据效力层级

| 存证方式 | 证据效力 | 成本 | 适用场景 | 法院认可度 |
|---------|---------|------|---------|-----------|
| **公证保全** | ⭐⭐⭐⭐⭐ 最高 | 高（500-2000元/次） | 诉讼前关键版本 | 100% |
| **司法鉴定** | ⭐⭐⭐⭐⭐ 最高 | 极高（1万-5万元） | 重大诉讼 | 100% |
| **区块链存证** | ⭐⭐⭐⭐☆ 高 | 低（10-50元/次） | 日常持续存证 | 高（《人民法院在线诉讼规则》第16条认可） |
| **可信时间戳** | ⭐⭐⭐★☆ 中高 | 低（10元/次） | 单一时间点证明 | 较高 |
| **Git版本控制** | ⭐⭐☆☆☆ 辅助 | 极低 | 内部管理 | 需配合其他证据 |

**推荐策略**：日常开发采用"区块链存证+Git"，关键里程碑采用"公证+区块链"，诉讼前采用"司法鉴定"。

### 2.2 存证要素

每次存证必须包含以下要素：

| 要素 | 说明 | 技术实现 |
|------|------|---------|
| **内容哈希** | 代码文件的SHA-256哈希值 | Git内置 + 独立计算验证 |
| **时间证明** | 精确的UTC时间戳 | 区块链出块时间/TSA签名 |
| **权属标识** | 开发者身份+实验室权属声明 | 数字证书签名 |
| **版本信息** | Git commit hash + tag | 自动提取 |
| **代码快照** | 完整代码副本（加密存储） | IPFS/私有存储 |
| **开发日志** | 该版本的修改说明 | Git commit message |

## 三、分级存证策略

### 3.1 A级核心算法 - 最高级别存证

**存证对象**：Mat-GAN核心模型、力场参数优化算法、多尺度耦合框架

#### 存证流程（SOP-E-001）

```markdown
### 步骤1：开发阶段（每次重大更新）
- [ ] 开发者在本地完成代码修改
- [ ] 本地运行测试，确保通过全部单元测试
- [ ] 编写详细的commit message（中英文）
- [ ] 使用GPG密钥对commit进行签名

### 步骤2：代码审查
- [ ] 提交Merge Request（MR）
- [ ] 至少1名高级研究员审查
- [ ] PI（刘宇宙）最终批准
- [ ] 审查意见完整记录

### 步骤3：自动存证（CI/CD触发）
- [ ] MR合并后自动触发存证流水线
- [ ] 计算代码仓库完整哈希树
- [ ] 生成代码结构图谱（函数/类依赖关系）
- [ ] 打包加密代码快照（AES-256）
- [ ] 调用区块链存证API，写入哈希+时间+权属
- [ ] 获取区块链交易哈希（TxHash）作为凭证

### 步骤4：双重备份
- [ ] 区块链存证：长安链/蚂蚁链（联盟链，司法认可）
- [ ] 公证处备份：季度批量公证（关键版本）
- [ ] 离线备份：加密U盘存入银行保险柜（年度）

### 步骤5：证据包生成
- [ ] 自动生成《算法版本存证报告》（PDF）
- [ ] 包含：哈希值、时间戳、TxHash、签名信息
- [ ] 存入证据管理台账
- [ ] 邮件通知PI和保密专员
```

### 4.1 区块链存证技术选型

| 平台 | 类型 | 司法认可度 | 成本 | 特点 |
|------|------|-----------|------|------|
| **长安链** | 联盟链 | ⭐⭐⭐⭐⭐ | 中 | 北京高院认可，政务场景 |
| **蚂蚁链** | 联盟链 | ⭐⭐⭐⭐⭐ | 中 | 最高法合作，司法证据平台 |
| **至信链** | 联盟链 | ⭐⭐⭐⭐⭐ | 低 | 腾讯系，互联网法院专用 |

### 4.2 存证智能合约核心逻辑

```solidity
// 简化版存证合约逻辑
struct Evidence {
    bytes32 contentHash;      // 内容SHA-256哈希
    uint64 timestamp;         // 存证时间戳
    address submitter;        // 提交者钱包地址
    string metadataURI;       // 元数据IPFS地址
    string rightsDeclaration; // 权属声明
    uint8 confidentialityLevel; // 保密级别 1=A, 2=B, 3=C
}

mapping(bytes32 => Evidence) public evidences;

function submitEvidence(
    bytes32 _contentHash,
    string memory _metadataURI,
    string memory _rightsDeclaration,
    uint8 _level
) public returns (bytes32 txHash) {
    require(evidences[_contentHash].timestamp == 0, "Evidence exists");
    
    evidences[_contentHash] = Evidence({
        contentHash: _contentHash,
        timestamp: uint64(block.timestamp),
        submitter: msg.sender,
        metadataURI: _metadataURI,
        rightsDeclaration: _rightsDeclaration,
        confidentialityLevel: _level
    });
    
    emit EvidenceSubmitted(_contentHash, msg.sender, block.timestamp);
    return keccak256(abi.encodePacked(_contentHash, block.timestamp));
}
```

### 4.3 CI/CD集成配置（GitLab CI示例）

```yaml
# .gitlab-ci.yml 存证阶段
stages:
  - test
  - build
  - evidence    # 新增存证阶段

evidence_job:
  stage: evidence
  only:
    - tags      # 仅在有tag时触发
  script:
    # 1. 计算代码哈希
    - CODE_HASH=$(git rev-parse HEAD)
    - TREE_HASH=$(git write-tree)
    
    # 2. 生成代码结构报告
    - python scripts/generate_code_map.py --output code-structure.json
    
    # 3. 打包加密快照
    - tar czf code-snapshot.tar.gz src/
    - openssl enc -aes-256-cbc -salt -in code-snapshot.tar.gz -out code-snapshot.enc -pass pass:$SNAPSHOT_KEY
    
    # 4. 上传IPFS（私有网关）
    - IPFS_HASH=$(ipfs add -q code-snapshot.enc)
    
    # 5. 区块链存证
    - python scripts/blockchain_evidence.py 
        --content-hash $TREE_HASH 
        --metadata-uri "ipfs://$IPFS_HASH" 
        --rights "知识产权归和光智成所有" 
        --level 1  # A级
        --output evidence-result.json
    
    # 6. 生成存证报告
    - python scripts/generate_evidence_report.py 
        --input evidence-result.json 
        --output "存证报告-$CI_COMMIT_TAG.pdf"
    
    # 7. 存档
    - cp "存证报告-$CI_COMMIT_TAG.pdf" /evidence-archive/
  
  artifacts:
    paths:
      - "存证报告-*.pdf"
      - evidence-result.json
```

## 五、证据管理与使用

### 5.1 证据台账管理

```sql
-- 证据数据库表结构
CREATE TABLE algorithm_evidence (
    id INT PRIMARY KEY AUTO_INCREMENT,
    evidence_no VARCHAR(32) UNIQUE,      -- 存证编号
    algorithm_name VARCHAR(200),          -- 算法名称
    version VARCHAR(50),                  -- 版本号
    confidentiality_level ENUM('A','B','C'), -- 保密级别
    content_hash VARCHAR(64),             -- 内容哈希
    blockchain_type VARCHAR(50),          -- 区块链类型
    tx_hash VARCHAR(66),                  -- 交易哈希
    block_number BIGINT,                  -- 区块高度
    timestamp DATETIME,                   -- 存证时间
    submitter VARCHAR(100),               -- 提交者
    metadata_uri VARCHAR(200),            -- 元数据地址
    notary_status ENUM('none','pending','completed'), -- 公证状态
    notary_cert_no VARCHAR(100),          -- 公证书号
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 5.2 诉讼证据包准备

当发生侵权诉讼时，快速生成证据包：

```markdown
### 证据包内容清单
1. **权属证据**
   - 劳动合同/职务创作声明
   - 算法开发日志（Git history）
   - 区块链存证证书

2. **秘密性证据**
   - 代码分级清单（本文件）
   - 保密协议签署记录
   - 访问权限控制记录

3. **价值性证据**
   - 算法商业应用证明（合同/产品）
   - 研发投入记录（工资/设备）
   - 技术评估报告

4. **侵权行为证据**
   - 对方产品/代码对比分析
   - 接触可能性证明（前员工/合作方）
   - 司法鉴定报告

5. **损失证据**
   - 利润损失计算
   - 维权费用清单
   - 许可费参考
```

### 5.3 证据验证流程

```
验证方（法院/对方当事人）
    │
    ▼
获取存证报告（含TxHash）
    │
    ▼
区块链浏览器查询交易
    │
    ▼
核对：交易时间、提交者地址、内容哈希
    │
    ▼
获取代码快照（IPFS/私有存储）
    │
    ▼
重新计算SHA-256，与链上哈希比对
    │
    ▼
哈希一致 → 存证有效，确认代码存在性及时间
```
