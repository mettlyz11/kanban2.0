## 一、Sprint生命周期

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  Sprint规划  │→│  执行与日站 │→│  评审与复盘  │
└─────────────┘  └─────────────┘  └─────────────┘
      2h              10天             1.5h
```

## 二、Sprint规划会议 (Day 0)

### 2.1 议程（120分钟）
| 时间段 | 内容 | 负责人 |
|--------|------|--------|
| 0-15min | 回顾上个Sprint速度（Velocity） | Scrum Master |
| 15-45min | 产品待办列表（PBL）梳理 | PO |
| 45-90min | 任务拆解与估算 | 团队 |
| 90-110min | 确定Sprint目标与承诺 | 团队 |
| 110-120min | 容量确认与风险识别 | 全体 |

### 2.2 任务拆分标准

✅ **INVEST原则**:
- **I**ndependent: 任务独立，不依赖其他Sprint任务
- **N**egotiable: 细节可协商
- **V**aluable: 对目标有明确价值
- **E**stimable: 可估算工时
- **S**mall: ≤ 8 小时（1人天）
- **T**estable: 有明确的完成标准

## 三、每日站会 (Daily Standup)

### 3.1 会议规则
- **时间**: 每日 10:00
- **时长**: 严格 ≤15 分钟
- **参与人**: 所有团队成员
- **站立进行**: 保持专注和高效

### 3.2 三个核心问题
```
1. 昨天我完成了什么？
2. 今天我计划做什么？
3. 我遇到了什么障碍（Blocker）？
```

### 3.3 阻塞升级机制
- 阻塞 < 4h → 自行解决
- 阻塞 4-24h → 站会同步，寻求帮助
- 阻塞 > 24h → 自动升级到 Scrum Master，2h内响应

---

## 四、Sprint评审会议 (Sprint Review)

### 4.1 议程（90分钟）
| 时间段 | 内容 |
|--------|------|
| 0-10min | Sprint目标回顾 |
| 10-50min | 交付物演示与验收 |
| 50-70min | 利益相关者反馈 |
| 70-90min | Backlog 更新 |

### 4.2 验收标准（DoD - Definition of Done）
- [ ] 代码/文档完成并提交
- [ ] 通过自动化测试（如有）
- [ ] 代码 Review 通过（如有）
- [ ] 产出文档/交付物齐全
- [ ] 任务状态更新为 "completed"
- [ ] result_summary 填写完毕（≥50字）

---

## 五、Sprint回顾会议 (Retrospective)

### 5.1 议程（60分钟）
| 时间段 | 内容 | 工具 |
|--------|------|------|
| 0-10min | 设置阶段 | 安全氛围确认 |
| 10-25min | 收集数据 | 开始/停止/继续 |
| 25-45min | 产生见解 | 5 Whys 根因分析 |
| 45-55min | 决定做什么 | SMART 改进项 |
| 55-60min | 收尾 | 感谢与总结 |

### 5.2 改进项跟踪
每个 Sprint 至少产出 **2-3 个可执行的改进项**，纳入下一个 Sprint。

## 六、看板流程与WIP限制

### 6.1 状态流转
```
待办 (Backlog)
  ↓ [Pull]
准备就绪 (Ready) → WIP = 5
  ↓
进行中 (In Progress) → WIP = 3
  ↓
代码/文档 Review → WIP = 2
  ↓
测试验证 (Testing) → WIP = 2
  ↓
✅ 完成 (Done)
```

### 6.2 在制品限制 (WIP Limits)
- **进行中**: 最多 3 项 → 避免多任务切换损耗
- **Review**: 最多 2 项 → 加速反馈循环
- **测试**: 最多 2 项 → 确保质量

## 七、燃尽图 (Burndown Chart)

### 7.1 计算公式
```
剩余工作量 = 总预估工时 - 已完成工时
理想线 = 总预估工时 × (Sprint总天数 - 当前天数) / Sprint总天数
```

### 7.2 异常判断
- 🟢 实际线 ≈ 理想线 → 正常推进
- 🟡 实际线 > 理想线 10-20% → 预警，关注阻塞
- 🔴 实际线 > 理想线 >20% → 警报，需要Scope调整

## 八、角色与职责

### Scrum Master
- 促进会议高效进行
- 移除障碍，保护团队
- 引导持续改进
- 维护看板流程

### Product Owner (PO)
- 定义产品愿景
- 维护待办列表优先级
- 澄清需求，验收成果
- 对ROI负责

### 团队成员
- 自组织，完成承诺
- 每日更新任务状态
- 主动暴露风险
- 参与持续改进

## 九、常见问题处理

### Q1: Sprint中间可以加需求吗？
A: **原则上不可以**。如果必须加，需要先移出同等工作量的其他任务，保持 Sprint 容量稳定。

### Q2: 发现任务估时不准怎么办？
A: 站会同步，团队共同评估影响。如果偏差 >50%，需要与 PO 讨论是否调整 Scope。

### Q3: 有人请假怎么办？
A: Sprint 规划时已预留 20% 缓冲。超过缓冲时，PO 决定降低哪些任务的优先级。

```
交付 [关键交付物1, 关键交付物2]，为下阶段 [里程碑] 奠定基础。
```

```
🎯 今天计划: [任务ID + 标题 + 预计工时]
🚧 阻塞点: [如有，描述 + 需要谁帮助]
```
