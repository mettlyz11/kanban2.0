## 1. 设计背景与核心原则

### 1.1 设计背景

随着分布式系统复杂度的指数级增长，单一代理模式已无法满足以下关键需求：

- **任务分解与并行执行**：复杂业务场景（如多源数据融合、实时风控决策）需要将任务拆解为多个子任务，由独立代理并行处理。
- **故障隔离与弹性伸缩**：单体代理故障可能导致全系统瘫痪，子代理架构允许局部故障不影响整体服务。
- **职责分离与专业化**：不同子代理专注于特定领域（如自然语言处理、规则引擎、数据清洗），提升执行效率与准确性。
- **可扩展性**：新功能可通过增加子代理实现，无需重构核心系统。

### 1.2 核心设计原则

1. **单一职责原则**：每个子代理仅负责一个明确的功能域，避免功能交叉耦合。
2. **无状态优先**：子代理内部尽量保持无状态，状态信息通过外部存储（如Redis、数据库）管理，便于水平扩展。
3. **异步通信**：所有代理间通信采用异步消息队列（如Kafka、RabbitMQ），避免同步阻塞导致系统延迟。
4. **优雅降级**：当子代理不可用时，系统应能通过缓存、默认值或备用代理继续运行，而非直接报错。
5. **可观测性内置**：每个子代理必须暴露健康检查、指标、日志和追踪接口，默认集成到监控系统。
6. **安全最小化**：子代理仅具备完成指定任务所需的最小权限，遵循零信任原则。

## 2. 子代理核心目标定义

### 2.1 总体目标

构建一套模块化、可编排、高可用的子代理系统，支持以下核心能力：

- **任务接收与解析**：接收来自主代理或用户的任务请求，解析为内部可执行指令。
- **领域化处理**：根据任务类型路由至对应子代理，执行特定领域逻辑。
- **结果聚合与返回**：将各子代理执行结果合并、校验后返回给调用方。
- **动态扩展**：支持运行时新增、移除或替换子代理，无需重启系统。

### 2.2 关键性能目标

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 任务平均处理延迟 | ≤ 200ms（P99 ≤ 500ms） | 从任务入队到结果返回的时间 |
| 系统吞吐量 | ≥ 10,000 任务/秒 | 每秒完成的任务数 |
| 子代理可用性 | ≥ 99.95% | 正常运行时间 / 总时间 |
| 任务失败率 | ≤ 0.1% | 失败任务数 / 总任务数 |
| 资源利用率 | CPU ≤ 70%，内存 ≤ 80% | 系统监控工具 |

## 3. 功能模块规格说明

### 3.1 子代理类型与功能矩阵

| 子代理名称 | 核心功能 | 输入 | 输出 | 依赖服务 |
|------------|----------|------|------|----------|
| Router Agent | 任务分类、路由决策 | 原始任务JSON | 路由指令、上下文ID | 规则引擎 |
| NLPAgent | 文本分析、意图识别、实体抽取 | 文本字符串 | 结构化意图数据 | 预训练模型服务 |
| RuleAgent | 规则匹配、条件评估、决策输出 | 结构化数据 | 决策结果、置信度 | 规则数据库 |
| DataCleanAgent | 数据清洗、格式标准化、去重 | 原始数据流 | 清洗后数据 | 数据字典 |
| AggregationAgent | 结果合并、冲突消解、最终输出 | 多个子代理结果 | 统一响应 | 缓存、数据库 |

### 3.2 各模块详细规格

#### 3.2.1 Router Agent

- **接口定义**：`POST /api/v1/route`，接收 `{ "task_id": "uuid", "payload": {...}, "type": "nlp|rule|clean" }`
- **路由规则**：基于 `type` 字段和规则引擎动态路由，规则示例：
  ```json
  {
    "rules": [
      { "condition": "type == 'nlp'", "target": "nlp_queue" },
      { "condition": "type == 'rule' && payload.priority > 5", "target": "rule_high_priority_queue" },
      { "condition": "default", "target": "default_queue" }
    ]
  }
  ```
- **错误处理**：若路由规则未命中，返回 `404` 并记录错误日志。

#### 3.2.2 NLPAgent

- **模型选型**：默认使用 `bert-base-chinese` 进行意图分类，`spaCy` 进行实体识别。
- **性能要求**：单次推理时间 ≤ 50ms，支持批量处理（最大 batch size = 32）。
- **示例代码**（Python）：

```python
from transformers import pipeline
import json

class NLPAgent:
    def __init__(self, model_name="bert-base-chinese"):
        self.classifier = pipeline("text-classification", model=model_name)
        self.ner = pipeline("ner", model="dbmdz/bert-large-cased-finetuned-conll03-english")

    def process(self, text: str) -> dict:
        intent = self.classifier(text)[0]
        entities = self.ner(text)
        return {
            "intent": intent["label"],
            "confidence": intent["score"],
            "entities": [{"word": e["word"], "entity": e["entity"]} for e in entities]
        }

# 使用示例
if __name__ == "__main__":
    agent = NLPAgent()
    result = agent.process("请帮我查询今天的天气")
    print(json.dumps(result, ensure_ascii=False))
```

#### 3.2.3 RuleAgent

- **规则存储**：规则以 JSON 格式存储在 PostgreSQL 或 Redis 中，支持热更新。
- **规则示例**：

```json
{
  "rule_id": 1001,
  "condition": "age > 18 && income > 50000",
  "action": "approve_loan",
  "priority": 1,
  "ttl": 3600
}
```

- **执行逻辑**：输入 `{ "age": 25, "income": 60000 }` → 匹配规则 1001 → 输出 `{ "decision": "approve_loan", "matched_rule": 1001 }`

#### 3.2.4 DataCleanAgent

- **清洗规则**：
  - 去除空值：若字段为 `null` 或 `undefined`，填充默认值或删除记录。
  - 格式校验：邮箱、电话号码、日期格式校验。
  - 去重：基于 `MD5(payload)` 哈希在 Redis 中存储 24 小时内已处理记录。
- **示例处理**：

```python
import hashlib
import redis

class DataCleanAgent:
    def __init__(self, redis_host="localhost", redis_port=6379):
        self.redis = redis.StrictRedis(host=redis_host, port=redis_port, decode_responses=True)

    def clean(self, record: dict) -> dict:
        # 1. 去重检查
        hash_key = hashlib.md5(str(record).encode()).hexdigest()
        if self.redis.get(hash_key):
            return {"status": "duplicate", "original": record}
        
        # 2. 字段清洗
        record["email"] = record.get("email", "").strip().lower()
        record["phone"] = "".join(filter(str.isdigit, record.get("phone", "")))
        
        # 3. 存储 hash 并设置 TTL
        self.redis.setex(hash_key, 86400, "processed")
        return {"status": "cleaned", "data": record}
```

#### 3.2.5 AggregationAgent

- **聚合策略**：
  - **优先级聚合**：按子代理优先级取结果（如 RuleAgent 结果优先于 NLPAgent）。
  - **加权投票**：若多个代理返回冲突结果，按权重计算最终决策。
  - **超时处理**：等待所有子代理结果，超时（默认 5 秒）则使用已返回结果。
- **示例输出**：

```json
{
  "task_id": "abc-123",
  "final_result": "approve_loan",
  "confidence": 0.95,
  "contributors": ["RuleAgent", "NLPAgent"],
  "warnings": ["NLPAgent returned low confidence (0.6)"]
}
```

## 4. 代理间通信与数据流转协议

### 4.1 通信协议

- **消息队列**：Apache Kafka（推荐）或 RabbitMQ，使用 Topic 模式。
  - Topic 命名规则：`subagent.{agent_name}.{action}`（如 `subagent.nlp.process`）
  - 消息格式：JSON，必须包含字段 `task_id`、`timestamp`、`payload`、`source`、`destination`
- **同步调用**：仅在必要场景（如健康检查）使用 HTTP/gRPC，超时设置为 1 秒。

### 4.2 数据流转示例

```
用户请求 → Router Agent (Kafka: subagent.router.in)
  ├─→ NLPAgent (Kafka: subagent.nlp.process)
  ├─→ RuleAgent (Kafka: subagent.rule.process)
  └─→ DataCleanAgent (Kafka: subagent.dataclean.process)
         ↓
AggregationAgent (Kafka: subagent.aggregation.process)
         ↓
最终响应 → 用户
```

### 4.3 消息格式模板

```json
{
  "task_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timestamp": "2024-07-15T10:30:00.000Z",
  "source": "RouterAgent",
  "destination": "NLPAgent",
  "payload": {
    "text": "请帮我查询今天的天气",
    "context_id": "ctx_001"
  },
  "metadata": {
    "priority": 5,
    "ttl": 300
  }
}
```

## 5. 职责边界划分与冲突解决机制

### 5.1 职责边界

| 子代理 | 不可越界行为 | 违规后果 |
|--------|--------------|----------|
| Router Agent | 不得修改 payload 内容 | 数据完整性异常 |
| NLPAgent | 不得执行规则匹配 | 逻辑错误 |
| RuleAgent | 不得修改输入数据 | 数据污染 |
| DataCleanAgent | 不得改变业务语义 | 业务规则违反 |

### 5.2 冲突解决机制

- **场景1：NLPAgent 与 RuleAgent 结果冲突**
  - 策略：RuleAgent 结果优先（业务规则 > 自然语言理解）
  - 实现：AggregationAgent 设置权重 `RuleAgent.weight = 0.7, NLPAgent.weight = 0.3`
- **场景2：多个 RuleAgent 规则冲突**
  - 策略：按规则优先级（priority 字段）排序，高优先级胜出
  - 若优先级相同，按规则触发时间排序，最近触发者胜出
- **场景3：数据清洗与业务规则冲突**
  - 策略：数据清洗仅处理格式问题，不修改业务关键字段（如金额、数量）

## 6. 可观测性与性能指标体系

### 6.1 日志规范

- 格式：JSON 结构化日志，包含 `timestamp`、`level`、`agent_name`、`task_id`、`message`、`duration_ms`
- 示例：
```json
{
  "timestamp": "2024-07-15T10:30:00.123Z",
  "level": "INFO",
  "agent_name": "NLPAgent",
  "task_id": "a1b2c3d4",
  "message": "Processed text successfully",
  "duration_ms": 45
}
```

### 6.2 指标暴露

每个子代理需暴露以下 Prometheus 指标（端口 9090）：

| 指标名称 | 类型 | 标签 | 说明 |
|----------|------|------|------|
| subagent_requests_total | Counter | agent, status | 总请求数 |
| subagent_request_duration_seconds | Histogram | agent | 请求延迟分布 |
| subagent_queue_depth | Gauge | agent | 当前队列深度 |
| subagent_errors_total | Counter | agent, error_type | 错误总数 |

### 6.3 健康检查

- **接口**：`GET /health`，返回 `{ "status": "healthy|degraded|unhealthy", "last_success_time": "..." }`
- **检查内容**：依赖服务（数据库、消息队列）连通性、模型加载状态、内存使用率

### 6.4 追踪

- 集成 OpenTelemetry，自动注入 Trace ID 和 Span ID 到所有日志和消息中。
- 示例 Span：`RouterAgent.route → NLPAgent.process → AggregationAgent.aggregate`

## 7. 架构约束与技术栈适配建议

### 7.1 架构约束

1. **语言约束**：子代理必须使用 Python 3.10+ 或 Go 1.20+ 编写，统一使用 gRPC 或 HTTP/2 进行同步通信。
2. **容器化**：所有子代理必须打包为 Docker 镜像，基础镜像使用 `python:3.11-slim` 或 `golang:1.21-alpine`。
3. **部署编排**：推荐使用 Kubernetes，每个子代理作为独立 Deployment，自动扩缩容基于 CPU 和内存指标。
4. **数据持久化**：子代理不得直接写入数据库，必须通过专用数据服务（如 Data Service API）操作。
5. **版本兼容**：子代理间通信协议版本号必须一致，升级时采用蓝绿部署策略。

### 7.2 技术栈推荐

| 组件 | 推荐技术 | 替代方案 |
|------|----------|----------|
| 消息队列 | Apache Kafka 3.5+ | RabbitMQ, NATS |
| 缓存 | Redis 7+ | Memcached |
| 数据库 | PostgreSQL 15+ | MySQL 8+ |
| 监控 | Prometheus + Grafana | Datadog, New Relic |
| 日志收集 | Elasticsearch + Logstash + Kibana | Loki + Grafana |
| 容器编排 | Kubernetes 1.28+ | Docker Swarm |

### 7.3 性能基准测试建议

- 使用 `locust` 或 `k6` 进行压力测试，模拟 10,000 并发用户。
- 测试场景：混合负载（50% NLP、30% Rule、20% Data Clean）。
- 目标：在 200ms 延迟内完成 95% 的任务。

## 8. 附录：术语表与典型应用场景映射

### 8.1 术语表

| 术语 | 定义 |
|------|------|
| 子代理 | 独立部署、专注于单一功能域的服务单元 |
| 主代理 | 负责任务分发和结果聚合的协调器 |
| 任务 | 由用户或系统触发的处理请求，具有唯一 ID |
| 上下文 | 跨多个子代理共享的状态信息，存储在 Redis 中 |
| 优雅降级 | 在部分组件不可用时，系统仍能提供有限服务的能力 |

### 8.2 典型应用场景映射

| 业务场景 | 涉及子代理 | 关键流程 |
|----------|------------|----------|
| 智能客服意图识别 | Router → NLP → Rule | 用户输入 → 意图分类 → 规则匹配 → 返回答案 |
| 金融风控决策 | Router → Data Clean → Rule → Aggregation | 交易数据 → 清洗 → 规则评估 → 聚合决策 |
| 多源数据聚合清洗 | Router → Data Clean × N → Aggregation | 多数据源 → 并行清洗 → 合并输出 |
| 实时告警系统 | Rule Agent × 多个规则 → Aggregation | 时间流 → 规则匹配 → 加权投票 → 触发告警 |
