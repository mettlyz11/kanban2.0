## 1. 任务背景与编号[04291803]关联范围说明

### 1.1 任务发起背景

本任务（编号04291803）由公司人力资源部于2024年7月10日发起，核心目标是对公司现有在职人员名单进行全面梳理与标准化清洗。本次梳理的直接驱动因素包括：

- **系统迁移需求**：公司计划于2024年Q3完成HR系统从旧版EHR系统向新一代云端HRIS系统的迁移，需确保迁移前人员数据的完整性与准确性。
- **合规审计要求**：根据《个人信息保护法》及ISO 27001信息安全管理体系年度审计要求，需对人员信息进行溯源与清洗记录留存。
- **组织架构调整**：2024年6月公司完成业务重组，涉及3个事业部合并与2个新部门设立，需同步更新人员归属信息。

### 1.2 关联范围界定

| 范围维度 | 包含内容 | 排除内容 |
|---------|---------|---------|
| 人员类型 | 全职正式员工、试用期员工、实习生（签订正式实习协议） | 劳务派遣人员、顾问、临时工、外部合作伙伴 |
| 地域范围 | 中国大陆地区（北京总部、上海、深圳、广州、成都、武汉分公司） | 海外子公司（新加坡、美国、德国） |
| 时间范围 | 截至2024年7月1日0:00在职状态的人员 | 已离职人员、长期休假超过6个月人员（保留在待处理清单） |
| 数据字段 | 工号、姓名、身份证号（脱敏）、部门、岗位、职级、入职日期、合同到期日、学历、联系电话（脱敏） | 薪资数据、绩效数据、银行账号（由财务系统独立管理） |

### 1.3 数据源范围

本次梳理涉及以下三个权威数据源，按优先级排序：

1. **EHR系统（Primary）**：公司正式HR管理系统，存储所有人员基础信息
2. **考勤系统（Secondary）**：用于验证在职状态与部门归属
3. **OA审批系统（Tertiary）**：用于确认岗位变动与入职日期

## 2. 人员筛选标准与边界界定

### 2.1 包含规则

**规则A - 在职状态确认**  
- 在EHR系统中状态为“在职”或“试用期”  
- 考勤系统最近30天有打卡记录（特殊岗位如外勤人员需提供主管签字确认）  
- 未在离职审批流程中（OA系统无待审批离职单）

**规则B - 合同有效性**  
- 劳动合同在有效期内（合同到期日 > 2024-07-01）  
- 对于无固定期限合同员工，自动视为有效

**规则C - 组织归属**  
- 部门字段不为空且在最新组织架构中存在  
- 岗位字段不为空

### 2.2 排除规则

**规则D - 特定状态排除**  
| 状态 | 排除原因 | 处理方式 |
|------|---------|---------|
| 长期病假（>3个月） | 需单独管理 | 移至“待处理-长期休假”清单 |
| 停薪留职 | 非正式在职状态 | 移至“待处理-停薪留职”清单 |
| 借调至外部单位 | 非公司直接管理 | 保留在名单但标记“借调” |

**规则E - 数据异常排除**  
- 身份证号校验失败（采用GB 11643-1999标准校验位算法）  
- 姓名包含不可见字符或全为空格  
- 工号重复（仅保留EHR系统中最后修改的记录）

### 2.3 例外情况处理

**例外1：新入职未完成信息录入**  
- 入职日期在2024年6月15日至7月1日之间，但EHR系统信息不完整  
- 处理方式：允许临时加入名单，标记为“待完善”，需在5个工作日内由HRBP补全信息

**例外2：实习生协议到期未续签**  
- 实习协议到期日在2024年6月15日至7月1日之间，但实际仍在岗  
- 处理方式：需部门负责人邮件确认，加入名单并标记“实习协议待续签”

**例外3：跨部门借调人员**  
- 人事关系在A部门，实际工作在B部门  
- 处理方式：以人事关系归属为准，但额外记录实际工作部门

### 3.2 数据清洗规则

#### 3.2.1 去重规则

**去重优先级**：工号 > 身份证号 > 姓名+手机号

```python
# 去重逻辑示例（伪代码）
def deduplicate_employees(records):
    # Step 1: 按工号去重，保留最后修改的记录
    by_employee_id = records.groupby('employee_id').apply(
        lambda x: x.sort_values('last_modified', ascending=False).iloc[0]
    )
    
    # Step 2: 检查身份证号重复
    id_duplicates = by_employee_id[by_employee_id.duplicated('id_number', keep=False)]
    for dup_id in id_duplicates['id_number'].unique():
        subset = by_employee_id[by_employee_id['id_number'] == dup_id]
        # 保留EHR系统中状态为“在职”的记录
        active = subset[subset['status'] == '在职']
        if len(active) == 1:
            by_employee_id = by_employee_id.drop(subset.index.difference(active.index))
        else:
            # 人工介入处理
            manual_review_list.append(subset)
    
    # Step 3: 姓名+手机号组合去重
    name_phone_duplicates = by_employee_id[
        by_employee_id.duplicated(['name', 'phone'], keep=False)
    ]
    # 记录到异常清单
    return by_employee_id, manual_review_list
```

#### 3.2.2 数据补全规则

| 缺失字段 | 补全来源 | 补全优先级 | 补全失败处理 |
|---------|---------|-----------|------------|
| 部门 | OA系统最新组织架构变动记录 | 高 | 标记为“部门待确认”，通知HRBP |
| 岗位 | 考勤系统岗位字段 | 中 | 标记为“岗位待确认” |
| 学历 | 员工入职时提交的学历证明（扫描件OCR） | 低 | 保留空值，标记“学历待补充” |
| 联系电话 | 考勤系统备用联系方式 | 中 | 标记“电话待更新” |
| 入职日期 | 劳动合同扫描件 | 高 | 由HRBP人工确认 |

#### 3.2.3 格式统一规则

**姓名格式**  
- 去除首尾空格  
- 中文字符统一为简体中文（使用opencc库转换）  
- 英文字符统一为全名（如“John Smith”而非“J. Smith”）  

```python
import re
import opencc

def normalize_name(name):
    # 去除多余空格
    name = re.sub(r'\s+', ' ', name).strip()
    # 简体中文转换
    converter = opencc.OpenCC('t2s')
    name = converter.convert(name)
    return name
```

**身份证号格式**  
- 统一为18位（15位身份证号自动转换为18位）  
- 末位X统一为大写  
- 执行GB 11643-1999校验位验证  

**日期格式**  
- 统一为YYYY-MM-DD格式  
- 时间戳转换为日期（去除时分秒）  

**电话号码格式**  
- 去除分隔符（-、空格、括号）  
- 手机号统一为11位数字  
- 座机号统一为“区号+号码”格式

## 5. 名单动态维护机制与定期更新建议

### 5.1 日常维护机制

**5.1.1 新增人员流程**  
- 员工入职后，HRBP需在3个工作日内完成EHR系统信息录入  
- 系统自动触发校验规则（身份证、手机号、邮箱格式）  
- 校验通过后，自动加入人员名单  
- 校验失败时，通知HRBP修正

**5.1.2 人员变动处理**  
| 变动类型 | 触发条件 | 处理时限 | 责任人 |
|---------|---------|---------|--------|
| 离职 | 离职审批完成 | T+1日从名单移除 | HRBP |
| 转岗 | 组织架构变动审批 | T+3日更新部门/岗位 | HRBP |
| 合同续签 | 合同到期前30天提醒 | 到期前完成更新 | HRBP |
| 信息变更 | 员工自助提交 | T+1日自动更新 | 员工本人 |

**5.1.3 异常监控告警**  
- 每日自动扫描名单，检测以下异常：
  - 身份证号失效（根据校验算法）
  - 部门在最新组织架构中不存在
  - 合同到期未续签（提前30天预警）
  - 考勤记录异常（连续15天无打卡记录）
- 异常告警通过企业微信推送给对应HRBP
