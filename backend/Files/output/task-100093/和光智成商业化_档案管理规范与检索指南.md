## 第一章 归档架构设计原则与目录说明

### 1.1 设计原则

本项目归档架构遵循以下五项核心原则：

1. **分类清晰性**：按业务属性将产出物划分为独立模块，避免交叉重叠
2. **层级合理性**：目录层级控制在三级以内，确保快速定位
3. **版本可追溯**：每个文件保留历史版本，支持任意时刻回溯
4. **安全合规性**：敏感文件与普通文件分离管理，落实权限控制
5. **扩展兼容性**：预留目录接口，适应项目演进需求

## 第二章 文件命名、格式与分类标准

### 2.1 文件命名规范

**命名公式**：`[项目代码]_[模块代码]_[文档类型]_[版本号]_[日期]_[描述].扩展名`

| 组成部分 | 编码规则 | 示例 |
|---------|---------|------|
| 项目代码 | 取拼音首字母大写 | `HGCZ`（和光智成） |
| 模块代码 | 两位数字+模块名 | `RD`（研发）、`PM`（产品） |
| 文档类型 | 英文或拼音缩写 | `SRS`（需求规格说明） |
| 版本号 | `V主版本.次版本` | `V1.0`、`V2.1` |
| 日期 | `YYYYMMDD`格式 | `20240115` |

**正确示例**：
```
HGCZ_RD_SRS_V1.0_20240115_用户登录模块需求.docx
HGCZ_PM_UX_V2.0_20240120_移动端高保真原型.axure
HGCZ_QA_TC_V1.2_20240125_接口测试用例.xlsx
```

**错误示例**：
```
和光智成项目需求.docx                    # 缺少编码
HGCZ需求文档V1.docx                      # 缺少分隔符
最终版_真的最终版_不改了.docx             # 描述冗余
```

### 2.2 文件格式标准

| 文档类型 | 推荐格式 | 备选格式 | 存储要求 |
|---------|---------|---------|---------|
| 文字文档 | `.docx` | `.pdf` | 必须保留可编辑版本 |
| 数据表格 | `.xlsx` | `.csv` | 禁用图片内嵌表格 |
| 设计图纸 | `.pdf` + `.axure` | `.fig`/.`sketch` | 需含导出PDF |
| 代码文件 | 源码格式 | `.zip`压缩包 | 按语言分类存放 |
| 图片截图 | `.png`/`.jpg` | `.webp` | 分辨率≥1920×1080 |
| 演示文稿 | `.pptx` | `.pdf` | 需含演讲者备注 |

## 第三章 新增/修改/废弃文件操作流程

### 3.1 新增文件流程

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  1.文件创建  │───▶│  2.命名规范 │───▶│  3.内容编写  │───▶│  4.自检合格  │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
                                                            │
                    ┌───────────────────────────────────────┘
                    ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  8.归档完成  │◀───│  7.版本锁定 │◀───│  6.审批通过 │◀───│  5.提交归档  │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

**操作步骤**：

| 步骤 | 责任人 | 操作内容 | 时限要求 |
|-----|-------|---------|---------|
| 1.文件创建 | 产出者 | 在对应模块目录创建文件 | - |
| 2.命名规范 | 产出者 | 按第二章规范重命名文件 | 当日完成 |
| 3.内容编写 | 产出者 | 按模板填写内容，填写文档头信息 | 按计划 |
| 4.自检合格 | 产出者 | 检查格式、完整性、排版 | 提交前 |
| 5.提交归档 | 产出者 | 上传至归档系统，填写归档申请表 | 完成后24h |
| 6.审批通过 | 模块负责人 | 审核内容准确性，审批通过 | 2个工作日 |
| 7.版本锁定 | 归档管理员 | 锁定正式版本，禁止修改 | 审批后 |
| 8.归档完成 | 归档管理员 | 更新索引目录，通知相关人 | 锁定后 |

### 3.2 修改文件流程

修改已归档文件必须走变更流程，保留全部历史版本：

**流程触发条件**：文件内容调整、版本升级、勘误补充

```
【变更申请】→【变更评审】→【版本更新】→【重新审批】→【归档更新】
```

**具体操作**：

1. **变更申请**
   - 填写《文件变更申请表》，说明变更原因、变更内容、影响范围
   - 申请表存储路径：`06_管理模块/01_项目计划/变更申请/`

2. **版本更新规则**
   - 修订标记：`_[修订序号]`
   - 重大变更：版本号主版本+1（如V1.0→V2.0）
   - 轻微修订：版本号次版本+1（如V1.0→V1.1）
   - 示例：`HGCZ_RD_SRS_V1.0_20240115.docx` → `HGCZ_RD_SRS_V1.1_20240201.docx`

3. **版本保留策略**
   - 保留最近5个正式版本
   - 保留全部变更记录表
   - 超过5个版本时，旧版本移至「历史归档区」

### 3.3 废弃文件流程

**废弃判定标准**：

- 文件内容完全过时且无参考价值
- 项目终止导致产出物失效
- 重复文件或错误文件
- 法规要求必须销毁的敏感文件

**废弃操作流程**：

```
【废弃申请】→【原因说明】→【影响评估】→【审批通过】→【执行废弃】→【注销登记】
```

| 步骤 | 操作内容 | 责任主体 |
|-----|---------|---------|
| 1.废弃申请 | 填写《文件废弃申请表》，说明废弃原因 | 申请人 |
| 2.原因说明 | 详细阐述废弃依据，提供佐证材料 | 申请人 |
| 3.影响评估 | 评估废弃对其他模块的影响 | 模块负责人 |
| 4.审批通过 | 审批人签字确认 | 项目经理 |
| 5.执行废弃 | 物理删除或移至废弃暂存区 | 归档管理员 |
| 6.注销登记 | 在索引表中标记「已废弃」，保留记录 | 归档管理员 |

**重要提示**：废弃操作不可逆，所有废弃记录保留不少于3年

## 第五章 定期审查机制与权限管理规范

### 5.1 定期审查机制

#### 5.1.1 审查类型与周期

| 审查类型 | 审查周期 | 审查内容 | 责任主体 |
|---------|---------|---------|---------|
| 日常巡检 | 每周 | 文件完整性、命名规范性 | 归档管理员 |
| 月度审查 | 每月 | 索引准确性、版本规范性 | 模块负责人 |
| 季度审计 | 每季度 | 归档流程执行、权限合理性 | 项目经理 |
| 年度清理 | 每年 | 历史文件清理、存储空间优化 | 管理层 |

#### 5.1.2 审查检查清单

**月度审查清单（示例）**：

- [ ] 检查新增文件命名是否符合规范
- [ ] 验证新增文件是否已提交归档申请
- [ ] 确认审批流程是否完整
- [ ] 核对索引表与实际文件是否一致
- [ ] 检查版本号连续性
- [ ] 排查重复文件或疑似重复文件
- [ ] 更新关键词索引

#### 5.1.3 审查输出

每次审查形成《审查报告》，包含：

1. 审查范围与时间
2. 发现问题清单
3. 问题分类统计（严重/一般/建议）
4. 整改措施与责任人
5. 下次审查关注点
