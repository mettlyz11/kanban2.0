## 1. 字段定义确认

### 1.1 字段列表与业务含义

| 字段名称 | 当前假设/提议 | 待确认事项 | 关键风险 |
|----------|--------------|------------|----------|
| lesson_id | 自增主键，用于唯一标识一条经验记录。假设格式为整数（INT） | 是否需要 UUID 或业务前缀？若后期跨数据库迁移可否兼容？ | 自增主键在分布式场景下可能冲突 |
| title | 字符串类型，最长 100 字符，必填。假设为经验标题 | 是否允许相同标题？字符长度上限是否足够？是否支持多语言？ | 标题重复可能导致检索混淆 |
| content | TEXT 类型，必填。存储经验详细描述 | 内容中是否允许嵌入图片/链接？字段长度是否有限制（如 64KB）？是否需要支持富文本（Markdown / HTML）？ | 内容过大影响性能，安全需要防 XSS |
| category_id | 外键，关联分类表。假设使用整数 ID | 是否必须绑定分类？若无合适分类如何处理？分类表是否已存在并稳定？ | 分类为空导致数据一致性风险 |
| tags | 逗号分隔的标签字符串或 JSON 数组。假设为 JSON 格式 | 标签来源：人工录入还是预定义库？标签数量上限？是否需要索引？ | JSON 字段查询效率低，无约束导致乱标签 |
| severity | 枚举值（严重、高、中、低）。假设为严重等级 | 是否必须填写？默认值取中？业务场景中是否需要“待分类”选项？ | 等级定义与用户理解可能不一致 |
| status | 枚举值（待审核、已发布、已归档、废弃）。假设初始为“待审核” | 工作流中哪些角色可以修改状态？状态转换规则是什么？ | 权限混乱导致未审核经验直接发布 |
| created_by | 用户 ID（整数），必填。假设从当前登录会话获取 | 是否记录匿名提交？历史数据迁移时用户 ID 如何映射？ | 外键级联删除是否影响 lessons 表 |
| created_at | 时间戳，自动生成。假设使用 UTC | 是否需要记录时区？前端展示是否统一转换成本地时间？ | 跨时区团队使用混乱 |
| updated_by | 用户 ID，可为空。假设最后修改者 | 更新时是否必须记录？批量更新场景下如何处理？ | 并发更新可能丢失更新者信息 |
| updated_at | 时间戳，自动更新。假设每次修改时记录 | 是否支持手动设置回旧时间（如数据修复）？ | 审计需求可能要求不可篡改 |
| source | 字符串，记录经验原始来源（如故障工单、项目复盘、外部资料）。假设为可选 | 是否需要标准化来源列表？来源字段是否适合做筛选指标？ | 来源命名不规范导致统计失效 |
| related_issue_id | 关联的问题工单 ID（整数），可为空。假设关联到 IT 工单系统 | 是否需要支持关联多个工单？若工单被删除则业务含义如何保持？ | 外键约束可能导致删除失败或孤儿记录 |

### 1.2 额外字段确认

1. **是否增加“经验类型”字段**（例如：技术方案、故障恢复、最佳实践、教训总结）？当前假设按 category_id 和 tags 混合实现，但可能需独立维度用于报表统计。
2. **是否需要“影响范围”字段**（如：单个系统、跨系统、部门级、公司级）？该项有助于高层评估风险，但会增加录入负担。
3. **是否保留“版本号”字段**？如果允许对已发布经验进行修订，则需版本管理以支持历史追溯。

## 2. 数据源确认

### 2.1 历史数据来源

| 来源系统 | 数据形式 | 记录数（估计） | 访问权限 | 当前假设 |
|----------|----------|----------------|----------|----------|
| IT 工单系统（Jira） | 工单描述、解决方案、备注 | ~5000 条 | 需项目经理授权 | 假设可以通过 API 导出，且字段对应关系明确 |
| 项目复盘文档（Confluence） | 富文本页面 | ~200 篇 | 全员可读 | 假设需要人工解析非结构化内容，无法自动化提取 |
| 个人知识库（Markdown 文件） | 本地 MD 文件 | ~150 篇 | 仅原所有者 | 假设需协调所有者主动提交或授权爬取 |
| 外部社区解决方案（Stack Overflow 收藏） | 网页链接 + 摘要 | ~80 条 | 公开 | 假设需要手动整理版权问题 |

### 2.2 待确认事项

- **数据清理与脱敏**：历史数据中是否包含客户信息、密码、密钥等敏感内容？迁移前必须执行脱敏，脱敏规则由安全团队确认。
- **数据质量**：假设历史数据存在重复、信息不全、格式不统一等问题。需要制定清洗标准，例如：重复定义（标题+内容相同视为重复）、必填字段缺失处理（补充默认值或抛弃）。
- **访问权限**：IT 工单系统 API 的调用频率限制？是否可以批量拉取全量数据？是否需要 DBA 协助导出为 CSV？
- **时间范围**：是否只沉淀近 3 年的经验，还是全部历史仓库？假设按“创建日期 > 2022-01-01”过滤，但需业务方确认。
- **历史责任人**：经验最初创建者可能已离职，created_by 字段如何映射到当前用户表？假设使用一个默认虚拟用户 ID（如 0）代表未知，但审计上需说明。

## 3. 业务规则确认

### 3.1 去重规则

| 规则 | 当前假设 | 待确认点 |
|------|----------|----------|
| 标题完全一致 | 视为重复，不允许插入 | 是否忽略大小写、空格、标点？ "数据库连接池耗尽"与"数据库连接池 耗尽"是否算重复？ |
| 内容相似度 > 90% | 可由算法识别重复后拦截并提示合并 | 相似度阈值是否可调？是否需要人工二次确认？ |
| 同一工单派生情况 | 同一故障工单可能产生多条经验（不同视角），不属于重复 | 是否在 source 字段中标明同一源头但不认为是重复？ |

### 3.2 优先级与排序规则

- **当前假设**：搜索结果默认按 severity（严重 > 高 > 中 > 低）排序，同级别的按 created_at 降序。
- **待确认**：是否将“被引用次数”或“点赞数”作为排序因子？是否支持用户自定义排序？是否需要置顶最新发布的经验？
- **优先级标识**：是否额外增加“紧急”标记（区别于 severity）以用于快速发布热点信息？

### 3.3 标签体系

| 维度 | 当前假设 | 待确认点 |
|------|----------|----------|
| 标签层级 | 扁平标签，无层级关系 | 是否需实现父子标签（如：数据库->MySQL->连接池）？若需，则需同步更新标签表设计。 |
| 标签来源 | 用户自由输入 + 系统推荐常用标签 | 是否设内置标签白名单避免乱标签？推荐算法如何实现？ |
| 标签数量限制 | 每条经验最多 5 个标签 | 是否需要放宽？若用户填入 10 个以上，前端是否提示限制？ |
| 标签颜色 | 无 | 是否在 UI 中根据标签分类显示不同颜色（如安全类红色）？这属于前端需求但影响数据字段设计。 |

### 3.4 状态流转规则

当前假设工作流为：  

> Draft（草稿）→ Pending Review（待审核）→ Published（已发布）  
> 已发布 → Archived（归档）或 Expired（废弃）  
> 废弃 → 不可逆（仅可查看历史）

待确认事项：

- 谁有权发布？谁有权审核？
- 是否支持“撤回”（Published → Draft）？
- 废弃后数据是否物理删除还是设置软删除标记（status = 'deleted'）？
- 是否有自动归档机制（如一年未修改且未被引用则自动归档）？

## 4. 使用场景确认

### 4.1 主要查询场景

| 场景编号 | 用户角色 | 查询目的 | 预期返回记录数 | 性能要求（响应时间） |
|----------|----------|----------|----------------|----------------------|
| S1 | 运维工程师 | 搜索特定系统（如支付系统）的已知问题及解决方案 | < 50 条 | < 0.5s |
| S2 | 项目管理者 | 按严重程度统计本月新增经验数 | < 30 条（聚合结果） | < 0.3s |
| S3 | 安全工程师 | 查询所有“安全”标签且严重度为“严重”的经验 | < 200 条 | < 1s |
| S4 | 普通员工 | 通过全文搜索查找包含“连接池”关键字的经验 | 未限制，但需要分页 | < 2s |
| S5 | 新员工 | 浏览“入门”推荐经验清单 | 10~20 条 | < 0.5s |

### 4.2 待确认事项

- **全文索引引擎**：当前假设使用 MySQL 的 FULLTEXT 索引，但需确认是否需集成 Elasticsearch 以支持更复杂的搜索（拼写纠错、同义词扩展）。
- **缓存策略**：对于热门查询（如今日推荐经验），是否允许 Redis 缓存？缓存失效时间多长？
- **报表需求**：是否有定期的数据报表（周/月报）需求？数据库 schema 是否需要反范式化以提升聚合查询性能？
- **并发量**：预估同时在线用户数？峰值 QPS ？假设小于 500 并发，但需运维确认实际负载。
- **API 接口**：经验库数据是否对外开放？是否需要设计 API 鉴权与限流？

## 5. 维护周期确认

### 5.1 数据更新频率

| 操作类型 | 当前假设 | 待确认点 |
|----------|----------|----------|
| 新增经验 | 每日平均 5~10 条 | 实际团队规模下是否可能更多？是否需要异步审批？ |
| 修改经验 | 每周 1~2 条修改 | 修改后是否需要重新审核？版本号递增？ |
| 删除经验 | 极少发生，仅由管理员操作 | 是否保留删除日志？ |
| 批量导入历史数据 | 一次性任务，限 2 周内完成 | 是否需要增量同步（如持续从工单系统抓取新工单）？若需要，则建成定时任务。 |

### 5.2 责任人确认

| 角色 | 职责 | 当前假设人员 | 待确认 |
|------|------|-------------|--------|
| 内容审核员 | 审核新经验，保证质量 | 团队 TL 轮流 | 是否设置专人？是否提供审核效率工具（推荐自动审核关键词）？ |
| 数据管理员 | 维护标签体系、处理异常数据 | DBA / 产品运营 | 是否有 SOP？是否需设置告警（如一天内无新经验）？ |
| 系统管理员 | 维护服务、监控性能、备份 | 运维团队 | 备份策略：每天全量备份 + 增量，保留 30 天 |
| 业务负责人 | 确认内容分类、优先级决策 | 项目经理 / 技术经理 | 是否设置定期回顾会议（如双周评审经验质量）？ |

### 5.3 待确认的周期性任务

- **过期清理**：是否设定经验“有效期”？例如 2 年后自动标记为“可能过时”，提醒作者检查更新。
- **数据归档**：数据超过 10 万条后，是否将旧数据（如创建超过 3 年且无引用）移动到历史表？
- **版本发布**：lessons 表结构变更（如新增字段）时，向前兼容策略是否明确？

## 6. 未覆盖事项（主动提出待确认补充）

1. **国际化与多语言**：是否需要支持中英文双语并存？字段上是否需要添加 locale 分离？
2. **附件支持**：是否允许上传图片、PDF 等文件作为经验辅助材料？若允许，存储选型（OSS / S3 / 本地）与安全扫描规则。
3. **用户反馈**：是否支持对经验“点赞”、“踩”、“评论”等互动功能？这些功能将影响表结构扩展。
4. **审计日志**：对 lessons 表的所有 DML 操作是否需记录变更历史（由谁、何时、改了什么）？假设利用数据库的 binlog 或应用层记录操作日志，需确认合规要求。
5. **容灾与高可用**：如果 lessons 表所在数据库故障，业务中断等级如何？是否需要主从复制或跨区同步？
