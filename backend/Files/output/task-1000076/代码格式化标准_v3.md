## 1. 背景与目标

### 1.1 现状分析

在当前 SDS（Smart Data Studio）项目开发过程中，团队成员来自多个背景，包括不同公司经历与个人编码习惯。代码审查（Code Review）中频繁出现关于缩进风格、引号使用、分号必要性、import 顺序以及组件命名方式的格式争议。根据对近三个月（2025年1月–3月）代码审查数据的统计，格式相关评论占总评论数的 32%——其中缩进争议占 15%，引号分歧占 8%，import 排序争议占 6%，其余包括空格、行宽等琐碎问题。这些争议不仅消耗了审查者的精力（平均每次 PR 多花费 12–18 分钟），更导致部分合入延迟，影响迭代速度。

### 1.2 核心目标

本规范旨在：

- **消除格式争议**：通过一套统一、可自动执行的规则，确保代码审查聚焦于逻辑正确性、性能与可维护性，而非个人偏好。
- **提升代码可读性**：一致的格式降低认知负荷，使团队每位成员能够快速理解陌生模块。
- **降低新成员入职成本**：明确的规则配合自动化工具，使新开发者能在第一天即产出符合规范的代码。
- **支持渐进式迁移**：鉴于项目中存在大量历史代码，本规范不强制立即重写，而是提供逐步推广路径，避免引起开发停滞。

### 1.3 预期收益

| 指标                  | 当前值      | 目标值（实施后3个月） | 衡量方式                     |
|----------------------|------------|---------------------|-----------------------------|
| PR 中格式评论占比     | 32%        | <5%                 | Code Review 评论分类统计     |
| 平均 PR 审查耗时     | 45 分钟     | 30 分钟以下          | Git 仓库事件日志             |
| 新成员首次提交合规率 | 40%        | 90%以上             | 自动化 lint 检测通过率       |

## 2. 适用范围

### 2.1 技术栈限定

本规范适用于使用 **TypeScript + React** 的前端项目，尤其是 **SDS（Smart Data Studio）** 及其子模块。具体包括：

- `packages/*` 下的所有 TypeScript/React 源码
- `apps/*` 中的业务应用代码
- 测试文件（`.test.ts`, `.test.tsx`, `.spec.ts`, `.spec.tsx`）
- 配置文件（`.eslintrc.*`, `.prettierrc*`, `tsconfig.json` 等），但配置文件的格式优先级低于功能正确性（例如 JSON 文件不可随意添加注释）

### 2.2 不适用范围

- **非 TypeScript 文件**：如 `.css`、`.scss`、`.less`、`.json`（除上述提到的配置外）应遵循各自的标准规范（例如 PostCSS 配置）；本规范提供的格式化工具不会自动修改这些文件。
- **第三方依赖代码**：`node_modules`、`lib` 目录中的生成代码不受本规范约束。
- **历史遗留大文件**：对于超过 500 行且已有独立格式化历史的旧文件，允许阶段性采用“增量约束”（详见第 5 章），但任何新增或修改的代码必须符合本规范。

### 2.3 例外条款

若因特定库或框架的限制（例如某些第三方类型定义文件要求特定写法），项目组可通过技术决策记录（ADR）申请豁免，豁免期限不超过 30 天，到期需重新审核。

## 3. 缩进、引号、分号、行宽等核心规则

本章节规定了代码格式的基础原子规则，所有规则均可在 Prettier + ESLint 中对应配置。

### 3.1 缩进

- **方式**：使用空格，不使用 Tab 字符。
- **大小**：每级缩进 2 个空格。
- **连续缩进**：对于多行函数参数、动态展开对象或数组字面量，当一行无法容纳时，后续行相对于第一项缩进 2 个空格。

```typescript
// 正确示例
const result = api.getData({
  page: 1,
  pageSize: 20,
  filter: { status: 'active' },
});

// 错误示例：使用 tab 或 4 空格
const result = api.getData({
    page: 1,
    pageSize: 20,
});
```

### 3.2 引号

- **字符串**：统一使用**单引号**，包括 JSX 的属性值（JSX 中属性值默认强制单引号）。
- **模板字符串**：仅在需要嵌入表达式或跨行时使用反引号，禁止仅为了使用双引号而使用模板字面量。
- **双引号**：仅用于 JSON 文件或特殊语法要求（如 JSX 中某些属性值必须使用双引号，但本规范通过 Prettier 自动处理）。

```typescript
// 正确
const name = 'Alice';
const greeting = `Hello, ${name}!`;

// 错误
const name = "Bob";
const unused = `constant string no interpolation`;
```

### 3.3 分号

- **规则**：**不使用分号**（以省略为默认），除非特殊行首符号导致 ASI 错误。
- **特殊处理**：为防范自动分号插入（ASI）风险，ESLint 配置 `no-unexpected-multiline` 和 `semi: ['error', 'never']` 同时开启 `@stylistic/semi-style` 检查。当一行以 `(`, `[`, 或`` ` ``开始时，请在行首添加分号（通常通过工具自动修复）。

```typescript
// 正确（无分号）
const a = 2
const b = 3
;(function() {
  console.log(a + b)
})()

// 错误（未保护常见 ASI 陷阱）
const c = a + b
[1, 2, 3].forEach(item => console.log(item))  // 会被解析为 b[1,2,3].forEach(...)
```

### 3.4 行宽

- **最大行宽**：**100 个字符**。超过此长度应进行换行。
- **换行策略**：采用 Prettier 的默认“打印宽度”模式，自动在合理位置（如参数、对象属性之间）换行。对于特别长的 URL 或字符串，建议拆分为变量拼接或使用注释标记 `prettier-ignore`。

```typescript
// 自动换行示例
const longString =
  'This is a very long string that exceeds the maximum line width limit and needs to be wrapped automatically by Prettier.'

// 使用 prettier-ignore 的场景（仅在绝对必要时）
// prettier-ignore
const specialUrl = 'https://api.example.com/v3/data/export?format=csv&include_deleted=false&limit=1000&offset=0'
```

### 3.5 尾逗号

- **规则**：**始终使用尾逗号**（包括函数参数列表、对象、数组最后一项），以便于版本控制的 diff 更清晰。

```typescript
// 正确
const obj = {
  a: 1,
  b: 2,
}

// 错误
const obj = {
  a: 1,
  b: 2  // 缺少尾逗号，新增字段 c 会影响 diff
}
```

### 3.6 空格

- **括号内部**：圆括号内无空格，方括号内无空格，花括号内保留一个空格（对象字面量）。
- **操作符周围**：二元操作符（`+`, `-`, `=`, `===`, `&&` 等）两侧各保留一个空格，一元操作符紧贴操作数（`!`, `++`, `typeof`）。
- **关键字后**：`if`, `else`, `for`, `while`, `switch`, `catch` 后保留一个空格。
- **函数名与括号**：函数声明/调用的括号前无空格。

```typescript
// 正确
if (condition) {
  const result = a + b
}

function foo(bar) {
  return !bar
}

// 错误
if(condition) {  // 关键字后无空格
  const result = a+b  // 操作符周围缺少空格
}
```

### 3.7 换行

- **文件末尾**：每个文件结尾必须有且仅有一个空行（Unix 换行符）。
- **行尾序列**：统一使用 **LF**，禁止 CRLF。`.gitattributes` 中配置 `* text=auto eol=lf`。

### 3.8 对应工具配置

**Prettier 配置片段（.prettierrc.json）**：
```json
{
  "semi": false,
  "singleQuote": true,
  "tabWidth": 2,
  "useTabs": false,
  "trailingComma": "all",
  "printWidth": 100,
  "bracketSpacing": true,
  "jsxSingleQuote": true,
  "endOfLine": "lf"
}
```

**ESLint 补充规则（.eslintrc.cjs）**：
```javascript
module.exports = {
  extends: ['plugin:prettier/recommended'],
  rules: {
    'prettier/prettier': 'error',
    '@stylistic/semi-style': ['error', 'never'],
    'no-unexpected-multiline': 'error',
    'no-trailing-spaces': 'error',
    'comma-dangle': ['error', 'always-multiline'],
  },
}
```

## 4. Import 排序与组件命名约定

### 4.1 Import 排序

统一的 import 顺序能够帮助开发人员迅速定位依赖关系，避免因包顺序混乱导致的重复声明。本规范采用 **`import/order`** 插件，按以下分组规则排列（优先级从高到低，每组内按字母序）：

1. **外部包**（Node 内置模块 + npm 依赖）
2. **内部绝对路径**（`@sds/` 或 `src/` 开头）
3. **相对父级**（`../`）
4. **相对同级**（`./`）
5. **CSS 或资源文件** (`*.css`, `*.scss`, `*.svg` 等)

每个组之间用一个空行分隔。默认导出与命名导出不作区分，统一按字母序排列。

**正确示例**：
```typescript
// 外部包
import React, { useState } from 'react'
import { useQuery } from '@tanstack/react-query'

// 内部绝对路径
import { formatDate } from '@sds/utils/date'
import { Card } from '@sds/ui/Card'

// 相对父级
import { useAuth } from '../../hooks/useAuth'

// 相对同级
import { getConfig } from './config'
import { type AppProps } from './types'

// 样式/资源
import './Table.css'
```

**错误示例**（混合顺序、无空行、CSS 位置不当）：
```typescript
import { Card } from '@sds/ui/Card'
import React from 'react'  // 外部包应在最上，且应在 @sds 前
import { getConfig } from './config'  // 相对应在内部包后
import './style.css'  // 应在最后且与前一组有空行
```

### 4.2 组件命名约定

| 项                 | 约定                                    | 示例                          | 错误示例                |
|-------------------|----------------------------------------|-------------------------------|-------------------------|
| **React 组件**    | PascalCase，文件名与组件名一致            | `UserProfile.tsx` → `UserProfile` | `userProfile.tsx`       |
| **Hooks**         | 以 `use` 开头，camelCase                | `useFetchData.ts`             | `FetchDataHook.ts`      |
| **工具函数**       | camelCase，文件名描述功能                | `formatCurrency.ts` → `formatCurrency` | `format_currency.ts`    |
| **类型/接口**     | PascalCase，文件名以 `.types.ts` 结尾    | `User.ts` → `interface User {}` | `userType.ts`           |
| **枚举**           | PascalCase，枚举成员使用 PascalCase 或 UPPER_CASE（按团队偏好，本规范推荐 UPPER_CASE） | `enum Status { ACTIVE, INACTIVE }` | `enum status { active, inactive }` |
| **常量**           | 全大写蛇形（SCREAMING_SNAKE_CASE）       | `export const MAX_RETRY_COUNT = 3` | `export const maxRetryCount = 3` |

**组件文件命名附加规则**：
- 一个文件只导出一个主要 React 组件（default export），其他工具函数或子组件属于同一文件内部。
- 测试文件命名：`{ComponentName}.test.tsx` 或 `{ComponentName}.spec.tsx`，放置在与组件同级目录的 `__tests__` 文件夹中。

### 4.3 代码示例：完整组件文件

```typescript
// src/components/UserCard/UserCard.tsx
import React from 'react'
import { useTranslation } from 'react-i18next'

import { Card } from '@sds/ui/Card'
import { Avatar } from '@sds/ui/Avatar'
import { formatDate } from '@sds/utils/date'

import type { User } from './types'

interface UserCardProps {
  user: User
  showDetails?: boolean
}

export const UserCard: React.FC<UserCardProps> = ({ user, showDetails = false }) => {
  const { t } = useTranslation()

  return (
    <Card>
      <Avatar src={user.avatarUrl} alt={user.fullName} />
      <h3>{user.fullName}</h3>
      {showDetails && <p>{t('last_login', { date: formatDate(user.lastLoginAt) })}</p>}
    </Card>
  )
}
```

## 5. 渐进式推广和验证方法

### 5.1 推广阶段

考虑到项目代码库规模（约 15 万行 TypeScript）以及正在进行的开发任务，本规范不要求一次性全量修改历史代码，而是采用“分三步走”策略：

| 阶段 | 时间跨度 | 目标范围 | 执行方式 |
|------|----------|----------|----------|
| **Phase 1：新代码约束** | 第1–2周 | 所有新创建的源文件及 PR 中新增/修改的代码 | 开发环境集成 Prettier + ESLint 自动修复；CI 加入 lint 检查，失败阻断合并 |
| **Phase 2：热门文件迁移** | 第3–6周 | 过去3个月内被修改超过2次的文件（约 200 个文件） | 分批自动化格式化（按模块，每周 50 个文件），并增加 `git blame` 忽略提交标记 |
| **Phase 3：全量规范化** | 第7–10周 | 剩余所有源代码文件 | 创建独立格式化工单，由团队在非开发高峰期逐步执行，每个文件提交后保证快照一致性 |

### 5.2 验证方法

#### 5.2.1 本地开发环境

- **编辑器集成**：要求所有开发者安装 Prettier 和 ESLint 插件，启用“保存时自动格式化”（Format on Save）功能，禁用其他格式化插件（如 Beautify、JS-CSS-HTML Formatter）以防止冲突。
- **预提交钩子**：通过 husky + lint-staged 在 `pre-commit` 阶段自动对暂存文件运行 `eslint --fix` 和 `prettier --write`。

**lint-staged 配置示例（package.json 片段）**：
```json
{
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": ["eslint --fix", "prettier --write"],
    "*.{css,scss,json,md}": ["prettier --write"]
  }
}
```

#### 5.2.2 持续集成（CI）

- **GitHub Actions 检查**：每个 Pull Request 自动执行 `pnpm lint`（包含 Prettier 检查）。若存在格式问题，CI 会生成包含具体文件与行号的错误报告，并阻止合并。
- **快照对比**：对于阶段迁移的文件，使用 `prettier --check` 配合 `diff` 确定无格式遗留问题。迁移完成后，将文件列入“免检清单”
