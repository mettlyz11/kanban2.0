## 1. 文档概述

本实施路线图旨在响应《定时任务系统价值再评估：状态唤醒（诊断版）》的结论，将系统当前的“亚健康”状态转化为具体的治理行动。当前系统面临任务僵尸化、调度延迟高及缺乏统一监控等挑战。本方案通过短期止血、中期重构、长期机制建设三个维度，全面唤醒系统活力，确保业务调度的稳定性与可观测性。

## 2. 短期治理计划（1-2周）：止血与清理

**目标**：消除系统显性风险，释放无效占用的计算资源，恢复基础监控能力。

### 2.1 无效任务下线专项行动

根据2023年Q3的审计数据，当前集群中注册任务总数为1,248个，其中超过180天未触发且状态为“运行中”的僵尸任务占比约15%。这些任务不仅污染控制台，还可能导致调度器线程池资源的无效争抢。

#### 2.1.1 数据诊断与清洗（SQL执行脚本）

以下SQL脚本用于识别并标记待下线的“僵尸任务”。请在执行前备份数据库。

```sql
-- 步骤1：识别僵尸任务（超过180天未执行，且非暂停状态）
SELECT 
    task_id,
    task_name,
    owner,
    last_execute_time,
    status
FROM 
    scheduled_task_info
WHERE 
    status = 'RUNNING' 
    AND last_execute_time < DATE_SUB(NOW(), INTERVAL 180 DAY)
    AND create_time < DATE_SUB(NOW(), INTERVAL 6 MONTH);

-- 步骤2：生成下线工单记录（插入审计表）
INSERT INTO task_offline_audit (task_id, task_name, reason, created_by, status)
SELECT 
    task_id, 
    task_name, 
    '长期未执行且无心跳，判定为僵尸任务', 
    'SYSTEM_AUTO_DIAGNOSE', 
    'PENDING_CONFIRM'
FROM 
    scheduled_task_info
WHERE 
    status = 'RUNNING' 
    AND last_execute_time < DATE_SUB(NOW(), INTERVAL 180 DAY);

-- 步骤3：批量软删除（修改状态为DEPRECATED，而非物理删除，保留30天）
UPDATE scheduled_task_info
SET status = 'DEPRECATED',
    update_time = NOW(),
    remark = '价值再评估-短期治理批量下线'
WHERE 
    status = 'RUNNING' 
    AND last_execute_time < DATE_SUB(NOW(), INTERVAL 180 DAY);
```

#### 2.1.2 执行流程
1.  **通知期（Day 1-2）**：向任务Owner发送邮件通知，要求在48小时内确认任务是否保留。逾期未响应视为同意下线。
2.  **灰度下线（Day 3-5）**：将确认无用的任务状态置为 `PAUSED`，观察3天，确认无业务侧报错。
3.  **彻底归档（Day 6-7）**：执行状态置为 `DEPRECATED`，并从调度引擎的加载列表中移除。

### 2.2 高优先级异常修复

当前监控数据显示，每周约有40次因 `NullPointerException` 和 `TimeoutException` 导致的核心任务失败。

**修复策略**：
*   **熔断机制引入**：对于单次执行超过30分钟的任务，自动发送报警并强制中断，防止阻塞线程池。
*   **重试策略优化**：将非业务逻辑错误的异常（如网络抖动）重试次数从0次调整为3次，采用指数退避算法（Interval: 1min, 5min, 10min）。

## 3. 中期架构优化（1-3月）：技术栈升级与迁移

**目标**：解决原生调度器的并发瓶颈，引入成熟的分布式调度框架，提升系统的可扩展性。

### 3.1 技术选型决策：迁移至 XXL-JOB

经过对 OpenClaw 特性引入与 XXL-JOB 迁移的对比评估，考虑到社区活跃度、文档完善度及与现有 Spring Boot 生态的兼容性，决定全量迁移至 XXL-JOB 2.4.0。

**对比数据表**：

| 维度 | 现有系统 | OpenClaw (增强) | XXL-JOB 2.4.0 | 决策 |
| :--- | :--- | :--- | :--- | :--- |
| 路由策略 | 轮询 (单一) | 动态分片 (需自研) | 轮询/故障转移/分片广播 | **XXL-JOB** (开箱即用) |
| 监控界面 | 简陋 | 需定制开发 | 完善的Dashboard | **XXL-JOB** |
| 运维成本 | 高 (需维护老代码) | 中 | 低 | **XXL-JOB** |
| 依赖侵入 | 强耦合 | 中等 | 低 (注解驱动) | **XXL-JOB** |

### 3.2 迁移实施方案

#### 3.2.1 环境搭建（Week 1-2）
部署 XXL-JOB Admin 调度中心集群（2节点），配置 Nginx 负载均衡，数据库采用现有 MySQL 集群。

#### 3.2.3 灰度迁移策略（Week 3-8）
1.  **双轨运行期**：保留旧调度系统，新任务优先在 XXL-JOB 注册。旧系统逐步停止新任务注册。
2.  **流量切换**：按照业务优先级，从低频任务（日报统计）开始迁移，逐步过渡到高频核心任务（订单超时取消）。
3.  **回滚预案**：若 XXL-JOB 出现故障，通过脚本快速将任务路由规则切回旧系统（保留旧系统执行器2周作为热备）。
