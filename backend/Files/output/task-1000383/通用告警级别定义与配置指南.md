## 1. 告警级别分类原则与框架

### 1.1 分类原则

告警级别分类需遵循以下核心原则，以确保告警系统高效、可靠且不易造成警报疲劳：

- **业务影响优先**：级别定义首要依据是对用户或业务连续性的影响程度，而非技术指标本身的数值高低。
- **可操作区分**：每个级别应对应明确的响应动作与升级路径，避免级间重叠模糊。
- **动态降噪**：允许通过自愈、抑制或聚合机制自动降低告警处置优先级，减少人工介入。
- **可审计可追溯**：所有级别变更（如抑制、升级）均需记录日志，便于事后复盘。

### 1.2 四层分级框架

本指南采用经典的**四层告警分级模型**，其结构如下表：

| 级别 | 级别英文 | 标记颜色 | 责任响应时间 | 典型响应方式 |
|------|----------|----------|--------------|--------------|
| 致命 | Critical | 深红 | ≤ 5分钟 | 立即召集值班工程师、触发电话 / 短信 / 即时通讯强制通知 |
| 严重 | Major | 橙红 | ≤ 15分钟 | 立即通知团队负责人，并可能触发自动恢复脚本 |
| 警告 | Warning | 黄色 | ≤ 30分钟 | 通知相关组，进入T+1待办队列 |
| 信息 | Info | 蓝色 | 无强制要求 | 仅记录日志或仪表盘，不主动通知 |

**关键设计原则**：任何告警必须且仅可归属上述四个级别之一，不可自定义中间级别。

## 2. 严重级别定义（致命 / 严重 / 警告 / 信息）

### 2.1 致命（Critical）

- **定义**：导致核心服务完全不可用、数据丢失或重大资金损失的事件。
- **典型场景**：
  - 可用区/区域级宕机持续超过60秒
  - 数据库主库写入失败超过30秒
  - 支付接口错误率连续5分钟≥100%
  - 核心中间件节点全部挂掉
  - 成本中心预算超支达到当天预算的300%
- **响应要求**：立即确认，并在2小时内完成故障恢复或回滚。

### 2.2 严重（Major）

- **定义**：核心服务部分功能受损或性能严重下降，但主体可用；或潜在会演变为致命的异常。
- **典型场景**：
  - 单实例CPU使用率持续≥95%超过10分钟
  - API P99延迟超过10秒，影响范围>5%用户
  - 副本集主从切换后从库延迟超过30秒
  - 磁盘使用率≥85%且增长趋势明显
- **响应要求**：15分钟内响应，启动二级应急预案。

### 2.3 警告（Warning）

- **定义**：指标异常但未影响业务，或属于可预见的风险预警。
- **典型场景**：
  - 内存使用率连续5分钟≥80%
  - 单个节点HTTP 5xx错误率在1%~3%之间
  - 证书即将过期（离有效期不足30天）
  - 成本日预算使用率超过90%
- **响应要求**：30分钟内确认，进入工单系统，工作日内处理。

### 2.4 信息（Info）

- **定义**：正常但不常见的事件，或用于记录状态变更、任务完成通知。
- **典型场景**：
  - 部署流水线完成
  - 自动扩缩容触发或结束
  - 日志轮转或备份完成
  - 自愈脚本成功执行
- **响应要求**：不强制主动响应，仅作为审计或调试参考。

## 3. 阈值设计思路与参考值

### 3.1 设计思路

阈值设计应遵循 **“分级 + 动态 + 多窗口”** 原则：

- **分级**：不同严重级别使用不同阈值边界（如：Warn 80%、Crit 95%）
- **动态**：重要指标（如请求延迟）可根据时段、峰值预测自动调整基线阈值
- **多窗口**：避免瞬时抖动触发告警，使用持续满足条件的时间窗口（如持续 5 分钟）

### 3.2 通用参考阈值表（基于生产环境最佳实践）

| 指标 | 警告（Warning） | 严重（Major） | 致命（Critical） | 窗口 | 备注 |
|------|----------------|---------------|-----------------|------|------|
| CPU 使用率 | ≥80% | ≥90% | ≥95% | 300秒 | 核心服务可适当降低至 70/85/90 |
| 内存使用率 | ≥80% | ≥90% | ≥95% | 300秒 | 因Java堆等SLA不同可调整|
| 磁盘使用率 | ≥80% | ≥90% | ≥95% | 600秒 | 避免清洗任务误触发 |
| 网络延迟（P99） | ≥2s | ≥5s | ≥10s | 60秒 | 对支付等敏感业务降低上限 |
| 错误率（5xx） | ≥1% | ≥5% | ≥10% | 300秒 | 注意排除健康检查路径 |
| 请求队列深度 | ≥50 | ≥200 | ≥500 | 120秒 | 视服务处理能力调整 |
| 证书到期天数 | ≤30天 | ≤7天 | ≤1天 | 每日检查 | 自动生成工单 |

**注意**：以上数值为通用建议，需根据各自业务 SLO 做偏差校准。例如，金融交易类服务应将错误率致命阈值设为 0.1%。

### 3.3 动态基线阈值示例（以Prometheus规则为例）

```yaml
# prometheus告警规则片段：使用历史波动计算动态阈值
groups:
  - name: dynamic_threshold
    rules:
      - alert: HighLatencyAnomaly
        expr: |
          histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
          > (avg_over_time(histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))[30d]) * 1.5
          + stddev_over_time(histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))[30d]) * 3)
        for: 5m
        labels:
          severity: major
        annotations:
          summary: "P99延迟异常高于历史均值+3σ"
```

## 4. 自愈机制与自动化降噪策略

### 4.1 自愈机制

针对常见故障，预先编写自动化恢复脚本，当告警触发时立即执行。自愈脚本需包含安全熔断（如失败次数超限则停止自愈，转为人工介入）。

**典型自愈场景及脚本示例（Python + API调用）**：

```python
#!/usr/bin/env python3
"""
自愈调度器示例：重启异常Pod
输入：告警JSON（包含 namespace, pod, 触发次数）
输出：执行结果
"""
import subprocess
import sys
import json

ALERT_DATA = json.loads(sys.stdin.read())
namespace = ALERT_DATA.get("namespace")
pod_name = ALERT_DATA.get("pod")
retry_count = ALERT_DATA.get("retry", 1)

if retry_count >= 3:
    print("预警：已达到最大自愈次数，放弃自愈，转人工")
    subprocess.run(["echo", "触发人工通知...", "|", "curl", "-X", "POST", "http://oncall-api/incident"])
    sys.exit(2)

# 执行重启
result = subprocess.run(
    ["kubectl", "delete", "pod", pod_name, "-n", namespace],
    capture_output=True, text=True
)
if result.returncode == 0:
    print(f"成功删除Pod {pod_name}")
else:
    print(f"删除失败: {result.stderr}")
    sys.exit(1)
```

### 4.2 自动化降噪策略

降噪策略包括三种机制：

- **告警抑制（Inhibition）**：当高级别告警存在时，自动屏蔽同一维度下的低级别告警。例如，节点宕机后抑制该节点上的所有磁盘/内存告警。
- **告警聚合（Grouping）**：短时间内的相似告警合并为一条。例如，同一服务的多个实例延迟告警合并为一条，附带受影响实例列表。
- **告警静默（Silencing）**：针对已知的维护窗口或临时事件，设置静默规则。

**Prometheus Alertmanager 配置示例（抑制与聚合）**：

```yaml
route:
  receiver: 'default'
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  group_by: ['alertname', 'severity', 'cluster']  # 聚合维度
  routes:
    - receiver: 'critical-pager'
      match:
        severity: 'critical'
      repeat_interval: 1h

inhibit_rules:
  - source_match:
      severity: 'critical'
    target_match:
      severity: 'warning'
    equal: ['alertname', 'cluster']  # 仅抑制同类型警告
  - source_match:
      severity: 'major'
    target_match:
      severity: 'info'
    equal: ['job', 'instance']
```

## 5. 通知策略与升级规则

### 5.1 通知渠道矩阵

| 级别 | 主要渠道 | 备用渠道 | 升级条件 |
|------|----------|----------|----------|
| 致命 | 电话 + 短信 + 即时通讯 | 邮件 + 物理报警 | 5分钟内未确认 -> 升级至二级值班 |
| 严重 | 即时通讯（@团队负责人）+ 短信 | 邮件 | 15分钟内未确认 -> 升级至团队经理 |
| 警告 | 即时通讯（群组）+ 工单系统 | 邮件 | 30分钟内未确认 -> 自动提升为严重（需配置业务SLA） |
| 信息 | 仅记录至日志系统或仪表盘 | 无 | 无 |

### 5.2 升级规则定义（使用通用 DSL）

使用YAML定义值班轮换与升级路径：

```yaml
escalation_policies:
  - name: "primary-oncall"
    severity: critical
    steps:
      - target: "oncall-user"
        timeout: 5m
      - target: "manager"
        timeout: 10m
      - target: "vp"
        timeout: 15m
        notify_by: ["phone", "slack"]
  - name: "secondary-oncall"
    severity: major
    steps:
      - target: "oncall-group"
        timeout: 15m
      - target: "team-lead"
        timeout: 30m
```

## 6. 与成本监控系统的集成建议

### 6.1 成本告警级别定义

将成本数据纳入统一告警分级，避免预算超支导致业务中断。建议：

- **致命**：当日成本已超月预算的 300%，或单服务成本异常增长 > 500%
- **严重**：当日成本超月预算的 150%，或连续3天超日预算 120%
- **警告**：日预算使用率达到 90%，或月预算使用率达 80%
- **信息**：成本环比增长超过 10%（基线内）

### 6.2 集成架构

将云（如 AWS Cost Explorer）或自建成本系统的metrics输出为Prometheus metrics端点，然后通过现有告警规则引擎统一管理。

**示例：采集AWS成本指标并生成告警**

```python
# 使用boto3获取当天成本，推送到Prometheus Pushgateway
import boto3
import time
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

ce = boto3.client('ce', region_name='us-east-1')
registry = CollectorRegistry()
daily_cost = Gauge('aws_daily_cost', 'Current day cost in USD', ['service'], registry=registry)

today = time.strftime('%Y-%m-%d')
response = ce.get_cost_and_usage(
    TimePeriod={'Start': today, 'End': today},
    Granularity='DAILY',
    Metrics=['UnblendedCost'],
    GroupBy=[{'Type': 'DIMENSION', 'Key': 'SERVICE'}]
)
for item in response['ResultsByTime'][0]['Groups']:
    service = item['Keys'][0]
    cost = float(item['Metrics']['UnblendedCost']['Amount'])
    daily_cost.labels(service=service).set(cost)

push_to_gateway('http://prometheus-pushgateway:9091', job='aws_cost', registry=registry)
```

然后在Prometheus中定义告警规则（参考第3节阈值表）。

## 7. 附录：行业最佳实践与趋势参考

### 7.1 行业最佳实践

- **Google SRE 原则**：使用SLI/SLO定义告警，避免噪音。仅当SLO面临风险时发出高等级告警。
- **AWS 告警最佳实践**：采用复合告警（多条件与/或）减少误报；使用Composite Alarms聚合多个指标。
- **告警分级标准化**：提倡全公司统一分级标准（如NOC一级/二级/三级），避免各团队自定义。
- **告警疲劳防范**：定期通过“告警回顾会”分析误报率，优化阈值与自愈覆盖率。

### 7.2 趋势参考

- **基于机器学习的动态告警**：利用历史数据自动调整阈值，识别异常模式（如季节性波动下的真实异常）。
- **事件驱动的自动化运维（Event-Driven Automation）**：将告警作为触发自动化工作流的事件源，实现闭环自动化。
- **告警与AIOps融合**：通过因果关系分析自动屏蔽衍生告警，仅保留根因告警。
- **成本感知的告警策略**：在云原生环境下，将成本指标与性能、可用性同等对待，纳入统一告警体系。
