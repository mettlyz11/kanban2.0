## 1. 项目概述与整理范围

### 1.1 项目背景

知识大脑系统是企业级智能知识管理平台，旨在通过人工智能技术实现知识资源的智能化采集、存储、关联与检索。项目于2024年1月正式启动，目标是构建一个具备语义理解、知识图谱、智能问答能力的统一知识平台。

### 1.2 项目目标

- **知识整合**：整合分散在8个业务系统中的结构化与非结构化数据
- **智能检索**：实现基于语义理解的精准知识检索，召回率≥85%
- **知识图谱**：构建覆盖核心业务领域的企业知识图谱
- **智能问答**：提供7×24小时智能问答服务，准确率≥80%

### 1.3 整理范围

## 3. 详细决策记录表

### 3.1 技术选型：NLP引擎（TA-001）

| 项目 | 内容 |
|------|------|
| **决策时间** | 2024年1月15日 |
| **决策形式** | 技术评审会 |
| **议题** | 确定项目NLP引擎技术选型 |
| **提出背景** | 项目需要实现中文语义理解、实体识别、关系抽取等NLP能力，需在开源方案与商业方案之间做出选择 |

**方案对比**：

| 方案 | 优点 | 缺点 | 预估成本 |
|------|------|------|----------|
| 方案A：自研基于PyTorch的NLP模型 | 自主可控、可定制 | 研发周期长（预计6个月）、需要资深NLP工程师 | 120万元 |
| 方案B：采用百度智能云NLP服务 | API完善、准确率高、支持中文 | 依赖第三方、数据安全性需评估 | 80万元/年 |
| 方案C：采用阿里云NLP服务 | 生态完善、稳定性好 | 成本较高、定制能力有限 | 95万元/年 |

**最终结论**：采用方案B（百度智能云NLP服务），主要原因：
1. 项目工期紧张，自研方案无法满足进度要求
2. 百度NLP在中文语义理解领域具备明显优势
3. 优先验证业务可行性，后期可考虑切换

**遗留问题**：
- 需在合同中明确数据安全责任条款
- 需评估高并发场景下的API调用成本

**责任人**：技术负责人 张伟  
**状态**：已执行

### 3.2 知识图谱存储方案（TA-002）

| 项目 | 内容 |
|------|------|
| **决策时间** | 2024年2月20日 |
| **决策形式** | 架构评审会 |
| **议题** | 确定知识图谱数据存储技术方案 |

**方案对比**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 方案A：Neo4j图数据库 | 成熟稳定、社区活跃 Cypher查询语言友好 | 社区版有并发限制 集群方案成本高 | 中小规模图数据 |
| 方案B：JanusGraph分布式图数据库 | 支持分布式扩展 与Hadoop生态集成 | 学习曲线陡峭 运维复杂 | 大规模图数据 |
| 方案C：NebulaGraph | 国产开源、高性能、支持分布式 | 社区相对较新 | 大规模、高并发场景 |

**最终结论**：采用方案C（NebulaGraph），主要原因：
1. 预计图数据规模约5000万节点，需支持分布式
2. NebulaGraph性能优于Neo4j，成本低于JanusGraph
3. 国产开源便于技术支持

**责任人**：架构师 李明  
**状态**：已执行

| 方案 | 优点 | 缺点 |

| 方案C：单体+模块化设计 | 初期开发快、部署简单 | 后期扩展困难 |

**最终结论**：采用方案A（按业务领域拆分6个服务），具体拆分如下：

```
├── user-service（用户服务）
├── knowledge-service（知识服务）
├── graph-service（图谱服务）
├── search-service（检索服务）
├── qa-service（问答服务）
└── admin-service（管理服务）
```

- 知识检索P99延迟：1200ms（目标：500ms）

| 查询优化 | 引入查询结果缓存、限制返回字段 | 检索延迟-30% |
| 缓存优化 | 扩大Redis缓存容量、优化缓存命中率 | 问答响应-35% |
| 异步处理 | 复杂查询改为异步、消息队列削峰 | 并发能力+100% |
