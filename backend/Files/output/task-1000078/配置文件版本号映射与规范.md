## 2. 通用版本号命名规范

### 2.1 版本号格式

采用 **语义化版本 2.0.0**（[Semantic Versioning](https://semver.org/)）标准，格式为：

```
MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]
```

- **MAJOR**（主版本号）：当做了不兼容的 API 修改或重大功能重构时递增。  
- **MINOR**（次版本号）：当增加了向下兼容的功能时递增。  
- **PATCH**（修订号）：当做了向下兼容的问题修正时递增。  
- **PRERELEASE**（预发布标识）：可选，如 `-alpha.1`, `-beta.2`, `-rc.3`。  
- **BUILD**（构建元数据）：可选，如 `+20250315`，仅用于内部构建追踪，不参与优先级比较。

**示例**：  
- 正式发布版：`2.1.0`  
- 内部测试版：`2.1.0-alpha.1`  
- 发布候选版：`2.1.0-rc.2`  
- 带构建时间：`2.1.0+20250315`  

### 2.2 递增规则

- **MAJOR**：包含不向后兼容的 API 变更、架构重构、数据库 schema 不兼容改动。  
- **MINOR**：添加新功能但保持向后兼容；标记 `@Deprecated` 的功能不会移除。  
- **PATCH**：包含 bug 修复、性能优化、安全补丁，不引入新功能。  
- **PRERELEASE**：在正式发布前使用，版本号小于对应正式版（如 `2.1.0-alpha` < `2.1.0`）。  
- 一旦正式发布（无 PRERELEASE 后缀），不允许修改同一版本的内容。

### 2.3 环境与分支版本化规范

- **开发环境（dev）**：使用 `MAJOR.MINOR.PATCH-SNAPSHOT`，例如 `2.1.0-SNAPSHOT`。  
- **测试环境（staging）**：使用 `MAJOR.MINOR.PATCH-rc.N`（发布候选）。  
- **生产环境（prod）**：使用 `MAJOR.MINOR.PATCH`（正式发布版）。  
- **所有环境必须使用相同的 MAJOR.MINOR.PATCH 基准**，仅后缀不同以示区分。

### 2.4 配置文件中的版本号表示

- **所有配置文件**统一使用 **不带 `v` 前缀** 的纯数字点分格式，如 `2.1.0`。  
- 若需要标识环境或快照，按 2.3 节在版本号后附加后缀。  
- 对于非编程语言配置文件（如 `.env`、`Dockerfile` 中的 `LABEL`），同样遵循此格式。  
- 对于 `pom.xml` 和 `package.json` 等原生支持版本号的文件，直接使用规范格式，无需额外处理。

### 2.5 版本号与构建

- 构建版本号（如 `+20250315.123456`）仅用于 CI/CD 内部流水线，不出现在正式配置文件中。  
- 每次构建时，由 CI 系统自动生成 BUILD 元数据并附加到 `PACKAGE_VERSION` 环境变量中，但主配置文件仍保持语义版本。

### 4.2 更新建议

为维护版本号的一致性与可追溯性，提出以下可执行建议：

#### 4.2.1 短期修复（下一个 Sprint 内完成）

1. **统一格式**：将所有配置文件中版本号的 `v` 前缀移除，修改 `docker-compose.yml` 为完整三位数。  
   - 具体操作：修改 `.env` 中 `APP_VERSION=v2.1.0` → `APP_VERSION=2.1.0`；修改 `docker-compose.yml` 中 `image: myapp:2.0` → `image: myapp:2.1.0`。

2. **同步版本**：将 `application-prod.yml`、`package.json`、`config/module-a.properties` 的版本号与主配置 `application.yml` 对齐至 `2.1.0`。  
   - 注意：`package.json` 需同时更新 `version` 字段。

3. **增加缺失版本**：在 `kubernetes/namespace.yml` 的 `metadata.annotations` 中添加 `version: 2.1.0`，以便集群资源管理。

4. **环境后缀规范化**：将 `application-dev.yml` 中的 `2.1.0-DEV` 改为 `2.1.0-SNAPSHOT`；后续新建的 `application-staging.yml` 应使用 `-rc.N` 格式。

#### 4.2.2 中期改进（2-3 个 Sprint）

1. **自动化版本检查**：编写 CI/CD 流水线步骤，在 PR 合并前扫描所有配置文件中的版本号，检查是否统一。可使用自定义脚本（如 Python 或 Bash）正则匹配版本号模式并比对。  
   - 示例脚本（Python）：
   ```python
   import re, os
   files = ["config/application.yml", "package.json", ...]
   expected_version = "2.1.0"
   for f in files:
       with open(f) as fh:
           content = fh.read()
           match = re.search(r'(\d+\.\d+\.\d+)', content)
           if match and match.group(1) != expected_version:
               print(f"{f}: version mismatch {match.group(1)} != {expected_version}")
   ```

2. **版本号发布流程**：定义 Git 标签与配置文件版本的联动规则。每次发布正式版时，由发布经理执行以下步骤：  
   - 在所有配置文件中搜索版本号占位符，替换为新版本。  
   - 提交 PR，审核通过后合并至 `main` 分支。  
   - 打 Git tag（如 `v2.1.0`），触发 CI 构建并生成发行版。
