# 系统功能模块的可插拔架构技术方案

## 1. 背景与目标

### 1.1 背景

在大型分布式系统与企业级应用中，业务需求频繁变更、功能迭代速度加快，传统单体架构或硬编码集成方式已难以满足弹性扩展与快速交付的需求。系统需要支持在不同运行环境中动态添加、移除或更新功能模块，同时保证核心系统的稳定与安全。

当前系统面临以下挑战：
- 核心平台与业务模块紧密耦合，升级某模块需重新部署整个系统，停机时间长。
- 第三方或内部团队开发的新功能无法独立发布，必须与主版本捆绑。
- 缺乏统一的模块隔离机制，模块间冲突（如类加载冲突、资源争用）导致系统不稳定。
- 无法在不停机的情况下对特定模块进行灰度发布或故障隔离。

### 1.2 目标

本方案旨在设计一套“可插拔架构”，实现系统功能模块的**动态加载、卸载、更新**，并提供**安全隔离、生命周期管理、版本兼容**等核心能力。具体目标如下：

| 目标 | 说明 |
|------|------|
| 模块化与解耦 | 核心系统（微内核）与功能插件完全解耦，插件仅依赖预定义的接口 |
| 热插拔 | 支持运行时加载/卸载/更新模块，不影响其他模块及核心系统正常运行 |
| 安全隔离 | 模块运行在独立资源域（ClassLoader/容器），限制文件系统、网络、线程等资源 |
| 版本兼容 | 接口向后兼容，支持模块多版本共存与平滑升级 |
| 标准化接口 | 定义明确的服务接口、扩展点、事件通道，降低开发门槛 |
| 可观测性 | 模块状态、性能指标、日志统一收集与告警 |

## 2. 设计原则与约束

### 2.1 设计原则

- **最小内核原则**：微内核只负责模块注册、生命周期管理、基础通信、资源分配，不包含任何业务逻辑。
- **契约优先**：所有模块必须实现 `Plugin` 接口，并通过声明式元数据描述依赖、版本、资源需求。
- **隔离性优先**：每个模块拥有独立的 ClassLoader 实例（Java）或进程级隔离（Python/Go），避免类冲突和内存泄漏。
- **版本兼容性策略**：接口采用语义化版本（SemVer），核心系统提供 `@API(since="1.0")` 注解，弃用方法需保留至少两个大版本。
- **异步通信**：模块间通过发布/订阅事件总线或异步消息队列通信，避免直接调用导致耦合。

### 2.2 约束

| 约束项 | 具体限制 |
|--------|----------|
| 语言环境 | 当前核心系统基于 Java 17+，插件可使用 Java 或 Kotlin（JVM语言） |
| 部署环境 | Linux x86_64 容器 (Kubernetes)，单进程多线程 |
| 模块体积 | 单个模块 JAR 文件不超过 200MB，资源文件需随包发布 |
| 性能目标 | 热插拔操作在 2 秒内完成（无重IO 场景），模块间通信延迟 < 10ms |
| 安全限制 | 模块默认无网络权限，需显式申请 `NetworkPermission` |

## 3. 整体架构概述（微内核 / 插件模式）

本架构采用**微内核 + 插件**模式，核心系统（Micro Kernel）包含以下几个子系统：

```
┌─────────────────────────────────────────────────────────┐
│                     Micro Kernel                        │
│  ┌──────────────┐  ┌──────────────┐  ┌─────────────┐   │
│  │ PluginManager│  │ ExtensionReg │  │ ServiceBus  │   │
│  │ (加载/卸载)  │  │ (注册中心)    │  │ (事件/消息) │   │
│  └──────┬───────┘  └──────┬───────┘  └──────┬──────┘   │
│         │                  │                  │          │
│  ┌──────┴──────────────────┴──────────────────┴──────┐  │
│  │            Resource Isolation Container            │  │
│  │  (Child First ClassLoader + SecurityManager)       │  │
│  └────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
         ▲          │    │          ▲
         │          │    │          │
┌────────┴──────────┴────┴──────────┴────────────┐
│              Plugin Repository                   │
│  (文件系统 / Maven / 对象存储)                   │
│  ┌─────┐  ┌─────┐  ┌─────┐                     │
│  │P1   │  │P2   │  │P3   │ ...                  │
│  └─────┘  └─────┘  └─────┘                     │
└───────────────────────────────────────────────-─┘
```

### 3.1 角色定义

- **Plugin**：功能模块的打包单元，包含 `plugin.yaml` 描述文件、接口实现类、依赖资源。
- **PluginManager**：核心组件，负责扫描插件目录、加载、卸载、启动、停止插件，维护插件状态机。
- **ExtensionRegistry**：管理插件暴露的服务与扩展点，提供服务查找与绑定。
- **ServiceBus**：基于事件驱动的轻量级通信总线，支持同步请求/响应与异步发布/订阅。
- **Resource Isolation Container**：为每个插件创建独立的类加载器（`PluginClassLoader`），并配置沙箱安全策略（`PluginSecurityPolicy`）。

### 3.2 状态机

插件实例具有以下生命周期状态：

```
UNLOADED → LOADING → RESOLVED → STARTING → ACTIVE
                  ↑         ↓         ↓
              UNRESOLVED   STOPPING → STOPPED
                                ↑
                           UNINSTALLED
```

状态转换由 `PluginManager` 驱动，每一步均可触发回调（`PluginLifecycleListener`）。

## 4. 核心接口与抽象层定义

### 4.1 `Plugin` 接口

所有插件必须实现 `com.system.plugin.Plugin` 接口：

```java
public interface Plugin {
    void init(PluginContext context);
    void start();
    void stop();
    void destroy();

    // 插件元数据
    PluginDescriptor descriptor();
}
```

### 4.2 `PluginDescriptor`

描述插件身份、版本、依赖、资源限制：

```java
public record PluginDescriptor(
    String id,                // 唯一标识, e.g., "com.example.fraud-detection"
    SemanticVersion version,  // 1.2.0
    String name,
    String description,
    List<PluginDependency> dependencies,
    ResourceConstraints resources,
    List<String> providedServices // 接口全限定名
) {}
```

### 4.3 `ExtensionPoint` 注解

用于标记可被插件扩展的接口：

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface ExtensionPoint {
    String name() default "";
    String since() default "1.0";
    boolean deprecated() default false;
}
```

### 4.4 `PluginContext`

提供给插件的运行环境，包含 ServiceBus、配置服务、日志服务、资源访问代理：

```java
public interface PluginContext {
    ServiceBus serviceBus();
    ConfigurationService config();
    Logger logger(String name);
    <T> T getService(Class<T> serviceClass);
    ResourceProxy resources(); // 受限的文件/NIO 访问
}
```

### 4.5 服务定义示例

考虑一个“欺诈检测”插件，它需要实现 `FraudDetectionService` 接口：

```java
@ExtensionPoint(name = "fraud-detection", since = "1.0")
public interface FraudDetectionService {
    DetectionResult analyze(Transaction tx);
}
```

插件实现：

```java
public class DefaultFraudDetectionService implements FraudDetectionService {
    @Override
    public DetectionResult analyze(Transaction tx) {
        // 业务逻辑
        return new DetectionResult(false, 0.0);
    }
}
```

## 5. 模块注册与发现机制

### 5.1 插件描述文件 `plugin.yaml`

每个插件打包时必须包含 `META-INF/plugin.yaml`，示例如下：

```yaml
id: "com.example.fraud-detection"
version: "1.2.0"
name: "Fraud Detection"
description: "Real-time fraud analysis for transactions"
provider: "security-team"
dependencies:
  - id: "com.example.common-utils"
    version: ">=1.0.0"
    optional: false
resources:
  maxThreads: 2
  maxMemoryMB: 128
  requireNetwork: false
  allowedPaths: ["/tmp/fraud-model/"]
services:
  - "com.example.plugin.FraudDetectionService"
```

### 5.2 注册流程

1. **扫描**：`PluginManager` 定时扫描插件目录，或通过 REST API 接收上传。
2. **验证**：校验插件签名（JAR 完整性）、依赖是否满足、版本冲突检测。
3. **解析**：`PluginResolveService` 读取 `plugin.yaml`，生成 `PluginDescriptor`。
4. **注册**：将 `PluginDescriptor` 写入 `ExtensionRegistry`（内存中 ConcurrentHashMap + 持久化到数据库）。
5. **加载**：若系统配置为自动启用，则触发加载流程。

### 5.3 服务发现

核心系统或其他插件可通过 `ExtensionRegistry` 按接口类型查找服务：

```java
ExtensionRegistry registry = kernel.getExtensionRegistry();
FraudDetectionService service = registry.lookupService(FraudDetectionService.class);
// 或通过ID查找
service = registry.findPlugin("com.example.fraud-detection")
                  .getService(FraudDetectionService.class);
```

支持权重与轮询负载均衡，可通过 `@Weight(100)` 注解标记。

## 6. 热插拔生命周期管理（加载、卸载、更新）

### 6.1 加载流程（时序）

```
Client                PluginManager          ClassLoader          SecurityManager      Plugin Instance
  │                        │                       │                      │                      │
  │  deploy("plugin.jar")  │                       │                      │                      │
  │──────────────────────▶ │                       │                      │                      │
  │                        │  1. validate and           │                      │                      │
  │                        │     create descriptor      │                      │                      │
  │                        │──────────────────────▶ │                      │                      │
  │                        │  2. create PluginClassLoader (child-first)      │                      │
  │                        │──────────────────────────────────────────▶      │                      │
  │                        │  3. set security policy      │                      │                      │
  │                        │─────────────────────────────────────────────▶    │                      │
  │                        │  4. load class & instance                        │                      │
  │                        │──────────────────────────────────────────────────▶│                      │
  │                        │  5. call init(context)                          │                      │
  │                        │──────────────────────────────────────────────────│─────────────────────▶│
  │                        │  6. start()                                     │                      │
  │                        │──────────────────────────────────────────────────│─────────────────────▶│
  │                        │  7. register services                           │                      │
  │                        │     to ExtensionRegistry                        │                      │
  │                        │◀─────────────────────────────────────────────────│                      │
  │  OK + Plugin id       │                       │                      │                      │
  │◀──────────────────────│                       │                      │                      │
```

**关键代码片段**（简化）：

```java
public Plugin deployPlugin(Path jarFile) throws PluginException {
    PluginDescriptor descriptor = parsePluginYaml(jarFile);
    resolveDependencies(descriptor);
    PluginClassLoader classLoader = new PluginClassLoader(jarFile, parentClassLoader);
    classLoader.setSecurityPolicy(new PluginSecurityPolicy(descriptor.resources()));
    
    Class<?> pluginClass = classLoader.loadClass(descriptor.mainClass());
    Plugin plugin = (Plugin) pluginClass.getDeclaredConstructor().newInstance();
    
    PluginContext context = buildContext(descriptor, classLoader);
    plugin.init(context);
    plugin.start();
    
    // 注册服务
    for (String serviceName : descriptor.providedServices()) {
        Class<?> iface = loadInterface(serviceName);
        Object impl = plugin.getClass().newInstance(); // 或从 plugin 获取
        registry.registerService(descriptor.id(), iface, impl);
    }
    return plugin;
}
```

### 6.2 卸载流程

1. 调用 `plugin.stop()`，等待所有请求处理完毕（可配置超时）。
2. 从 `ExtensionRegistry` 中注销服务。
3. 断开与其他插件的绑定（事件总线取消订阅）。
4. 调用 `plugin.destroy()`。
5. 关闭 `PluginClassLoader` 并使其可被 GC。
6. 将插件状态改为 `UNINSTALLED`。

### 6.3 更新流程

采用**蓝绿部署**策略：
- 新版本插件以独立 ID（如 `com.example.fraud-detection:1.3.0`）部署。
- 旧版本保持运行，直到新版本就绪并通过健康检查。
- 通过 `ExtensionRegistry` 切换默认实现（依赖新版插件的订阅方自动重连）。
- 旧版本在无引用后停止并卸载。

## 7. 模块间通信与依赖管理

### 7.1 通信方式

| 通信方式 | 适用场景 | 实现 |
|----------|----------|------|
| 同步RPC | 服务调用（如插件A调用插件B的服务） | 通过 ExtensionRegistry 获取接口代理，内部使用动态代理 + 线程池隔离 |
| 异步事件 | 解耦通知（如交易完成事件广播） | ServiceBus 基于 Disruptor + 自定义 Topic |
| 共享内存 | 极高性能（如流式处理） | 只允许通过预定义的 `SharedDataRegion` 接口访问 |

**ServiceBus 示例接口**：

```java
public interface ServiceBus {
    <T> void publish(String topic, T event);
    <T> Subscription subscribe(String topic, EventHandler<T> handler);
    <T, R> R call(String serviceId, String method, Object... args); // 同步调用
}
```

### 7.2 依赖管理

- 依赖图由 `PluginManager` 构建，采用拓扑排序确保按顺序启动/停止。
- 循环依赖检测：加载时若检测到环，抛异常并拒绝部署。
- 可选依赖：`optional: true` 的依赖若缺失，插件仍可启动但功能受限。

## 8. 安全隔离与资源限制

### 8.1 ClassLoader 隔离

使用**Child-First 委托模型**：

```java
public class PluginClassLoader extends URLClassLoader {
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        // 先尝试从本地 JAR 加载（子优先）
        try {
            return findClass(name);
        } catch (ClassNotFoundException e) {
            // 再从父 ClassLoader 加载
            return super.loadClass(name, resolve);
        }
    }
}
```

但需注意：核心系统接口（如 `Plugin`、`ExtensionPoint`）应由父 ClassLoader 加载，避免 `ClassCastException`。因此，在 `PluginClassLoader` 中设置白名单类（`coreClasses`），这些类委托给父加载器。

### 8.2 资源限制

通过 `PluginSecurityPolicy` 实现沙箱：

```java
public class PluginSecurityPolicy extends Policy {
    private final ResourceConstraints constraints;
    
    @Override
    public boolean implies(ProtectionDomain domain, Permission permission) {
        // 根据插件 constraints 检查文件、网络、线程等
        if (permission instanceof FilePermission) {
            return allowedPaths.contains(permission.getName());
        }
        if (permission instanceof RuntimePermission("setSecurityManager")) {
            return false; // 不允许修改安全策略
        }
        // 其他默认拒绝
        return false;
    }
}
```

### 8.3 线程与内存限制

- 使用 `ThreadGroup` 隔离：所有插件线程放入唯一 `ThreadGroup`，可统一中断、监控。
- 内存通过 JVM `-Xmx` 与 `-Xss` 无法精确控制每个插件，可采用 **JVM 沙箱容器**（如 JUnit 5 的 Sandbox）或外部进程。本方案采用**监控 + 强制终止**：`PluginHealthChecker` 定期检查每个插件的内存使用（通过 `MemoryMXBean`），超过阈值则调用 `PluginManager.stopPlugin()` 并记录告警。
