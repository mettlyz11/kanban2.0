# v4 #7 调度防暴走机制说明

## 1. 概述

### 1.1 任务背景

V4 调度系统是公司核心任务编排引擎，负责将数据加工、模型训练、消息推送等数十万个定时及依赖触发的任务分发给计算节点执行。在 2024 年 Q2，生产集群连续发生三次“调度暴走”事件：由于某个用户误操作提交了重复任务组，或下游系统异常回路上报，导致调度器在短时间内为同一任务触发了数万次重复的执行请求，打满了消息队列，压垮了计算节点，并造成其他正常任务大面积延迟。

“调度防暴走”机制正是为应对此类风险而设计，其核心目标是在调度器层面建立 **频率限制** 与 **请求去重** 两道防线，从源头阻断异常的、重复的或过于频繁的任务调度请求，避免调度风暴波及下游，保障整体集群的稳定性和可用性。

### 1.2 防暴走目标

- **频率限制**：对同一任务（或同一用户、同一优先级维度）的调度请求进行速率控制，防止短时间内的爆发式提交。
- **请求去重**：在调度入口处识别并丢弃完全相同的重复请求，避免因幂等性缺失导致的任务多次执行。
- **快速熔断与恢复**：当触发防暴走规则时，能够记录告警、临时阻塞异常请求，并在恢复条件满足后自动放行，降低人工介入成本。
- **可观测性**：所有限流与去重事件需有清晰的日志、指标和告警，便于运维定位问题。

## 2. 频率限制机制

频率限制采用 **滑动窗口 + 令牌桶** 的混合模式，以任务全局唯一标识（`task_id`）为粒度，辅以用户级和优先级级的总量限制。

### 2.1 参数配置

频率限制相关的配置项定义在调度服务配置文件 `scheduler_config.yml` 中，主要参数如下：

| 参数名                                      | 类型   | 默认值      | 说明                                                         |
| ------------------------------------------- | ------ | ----------- | ------------------------------------------------------------ |
| `rate_limit.default.max_requests_per_window` | int    | 10          | 单个任务在滑动窗口内的最大调度请求次数                         |
| `rate_limit.default.window_seconds`          | int    | 60          | 滑动窗口的时间跨度（秒）                                       |
| `rate_limit.default.burst_max`               | int    | 20          | 令牌桶允许的突发最大请求数                                     |
| `rate_limit.default.refill_rate`             | float  | 1.0         | 令牌补充速率（个/秒）                                         |
| `rate_limit.user.max_requests_per_window`    | int    | 1000        | 单个用户（`owner`）全局滑动窗口最大请求数                      |
| `rate_limit.user.window_seconds`             | int    | 60          | 用户级窗口时间跨度                                            |
| `rate_limit.priority.high.max_per_window`    | int    | 500         | 高优先级任务在窗口内的全局限制（所有高优任务共享）             |
| `rate_limit.priority.low.max_per_window`     | int    | 100         | 低优先级任务全局限制                                           |

### 2.2 滑动窗口实现

采用 **固定队列 + 时间戳** 的滑动窗口算法，每个限流维度（`task_id`, `user`, `priority_group`）维护一个双向链表或循环数组，记录最近 `window_seconds` 秒内的请求时间戳。

**核心伪代码（Python）**：

```python
import time
from collections import deque

class SlidingWindowRateLimiter:
    def __init__(self, max_requests: int, window_seconds: int, burst_max: int = None):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        # 突发请求数（令牌桶模式）
        self.burst_max = burst_max if burst_max else max_requests
        self.queue = deque()
        self.tokens = self.burst_max  # 初始令牌数
        self.last_refill = time.time()

    def _refill_tokens(self):
        now = time.time()
        elapsed = now - self.last_refill
        new_tokens = elapsed * (self.max_requests / self.window_seconds)
        self.tokens = min(self.burst_max, self.tokens + new_tokens)
        self.last_refill = now

    def allow_request(self) -> bool:
        now = time.time()
        # 1. 清理过期时间戳
        while self.queue and self.queue[0] < now - self.window_seconds:
            self.queue.popleft()
        # 2. 检查队列长度（滑动窗口计数）
        if len(self.queue) >= self.max_requests:
            # 若窗口已满，再尝试令牌消耗（允许突发但受限于令牌）
            self._refill_tokens()
            if self.tokens >= 1:
                self.tokens -= 1
                self.queue.append(now)
                return True
            return False
        # 3. 窗口未满，直接放行
        self.queue.append(now)
        return True

# 使用示例：task_id = "task_engine_train_001"
rate_limiter = SlidingWindowRateLimiter(
    max_requests=10,
    window_seconds=60,
    burst_max=20
)

# 模拟请求
for i in range(15):
    print(f"Request {i+1}: allowed={rate_limiter.allow_request()}")
```

**说明**：
- 滑动窗口队列保证了时间范围内的绝对数量限制。
- 令牌桶模式在队列满时提供一定的突发容忍度，防止瞬间流量误杀，但要控制在 `burst_max` 内。
- 实际生产环境使用 Redis SortedSet 实现分布式限流，代码逻辑与此类似，仅存储层不同。

### 2.3 阈值计算与动态调整

- **静态阈值**：通过配置项直接设定。
- **动态阈值**：在系统压力较高时（如调度队列长度超过 80%），自动将 `max_requests_per_window` 缩减为原值的 50%，同时降低 `burst_max`。该功能由监控组件 `RateAdjuster` 定期（每 10 秒）计算并推送新值到 Redis，平滑生效。

## 3. 去重机制

去重机制用于识别并丢弃 **在短时间内重复提交的完全相同** 的调度请求。判定“相同”基于去重键（Dedup Key）的精确匹配。

### 3.1 去重键计算

去重键由以下字段按照固定格式拼接并做 SHA256 哈希后得到：

```
dedup_key = SHA256(task_id + "|" + trigger_type + "|" + trigger_id + "|" + scheduled_time + "|" + parameters_md5)
```

| 字段             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| `task_id`        | 任务唯一标识                                                 |
| `trigger_type`   | 触发类型：`cron` / `deps` / `manual` / `api`                 |
| `trigger_id`     | 触发源标识（如上游任务实例 ID 或用户 ID）                    |
| `scheduled_time` | 任务计划执行时间戳（秒级，精确到秒）                         |
| `parameters_md5` | 任务参数（JSON 格式）的 MD5 值（若参数为空则取空串 MD5）     |

示例：

```python
import hashlib
import json

def compute_dedup_key(task_id, trigger_type, trigger_id, scheduled_time, parameters: dict) -> str:
    params_md5 = hashlib.md5(json.dumps(parameters, sort_keys=True).encode()).hexdigest()
    raw = f"{task_id}|{trigger_type}|{trigger_id}|{scheduled_time}|{params_md5}"
    return hashlib.sha256(raw.encode()).hexdigest()

# 示例
key = compute_dedup_key(
    "task_predict_v2", "cron", "cron_1_2024_12_01_10_00",
    1733040000, {"model": "v3.2", "batch_size": 128}
)
print(key)  # 输出类似 "a1b2c3d4..."
```

### 3.2 缓存策略

去重使用 **Redis** 作为分布式缓存，设置如下：

- **数据结构**：String 类型，key 为 `dedup:{dedup_key}`，value 为 `1`。
- **过期时间（TTL）**：默认 **300 秒**（5 分钟），可通过配置 `rate_limit.dedup_ttl_seconds` 调整。
- **写策略**：使用 Redis `SET` 命令带上 `NX`（不存在则写入）和 `EX` 过期，原子操作。

如果 `SET NX` 返回 `OK`，说明该请求首次到达，允许通过；如果返回 `nil`，说明已经存在完全相同的请求，判定为重复，直接丢弃。

**关键考虑**：
- 过期时间不宜过长，防止因业务参数变化导致正常请求被误判为重复；也不宜过短，应覆盖调度器重试间隔。
- 极端情况下，若调度器短时间内收到两个完全相同的请求（例如上游重试两次），去重机制会保留第一个，丢弃第二个。

### 3.3 去重与频率限制的关系

去重是更严格的“完全一致”判断，频率限制是更宽松的“同一任务不能短时间太多请求”。二者互为补充：

- 去重在前：处理明显的重复请求，减少不必要的计数器写入。
- 频率限制在后：防止合法但高频的请求（如不同参数但同一任务的多个调度）压垮系统。

部署上，先去重，再走频率限制。

## 4. 防暴走流程

整个防暴走流程嵌入在调度请求处理的主链路中，从接收请求到最终下发执行节点之前。

### 4.1 触发条件

调度器接收到一个新的调度请求（`ScheduleRequest`）后，依次执行以下步骤：

1. **请求格式校验**：必填字段检查，参数 JSON 校验。
2. **去重检查**：计算 `dedup_key`，尝试 Redis `SET NX`。若失败，记录 `dedup_skip` 指标并返回错误码 `409 Conflict`，不执行后续逻辑。
3. **频率限制检查**：
   - 按 `task_id` 维度检查滑动窗口，若超过则触发任务级限流。
   - 按 `owner` 维度检查用户级限流。
   - 按 `priority` 维度检查优先级总限流。
   - 任意一级超过阈值，均返回 `429 Too Many Requests`。
4. **熔断检查**：若过去 5 分钟内该任务的限流拒绝率 > 20%（可配置），触发熔断——暂时阻塞该任务的所有请求 120 秒。
5. **决策结果**：若通过全部检查，请求进入调度队列；若被限流或去重，直接拒绝并记录原因。

### 4.2 告警

当出现以下情况时，发送告警通知（通过 Prometheus AlertManager + 企业微信 / 钉钉）：

- 同一 `task_id` 在 **1 分钟内** 被频率限制次数 ≥ 50 次。
- 同一 `user` 被频率限制次数 ≥ 200 次。
- 任何去重命中（`dedup_skip`）情况。
- 触发熔断状态进入或退出。

告警内容包含：限流维度、当前请求量、阈值、时间范围、上下文 task_id 等信息。

### 4.3 熔断恢复

熔断机制使用 **熔断器模式**（Circuit Breaker），状态变化如下：

- **CLOSED**（正常）：请求正常通过。
- **OPEN**（熔断）：所有请求直接拒绝，不消耗限流计数。
- **HALF-OPEN**（半开）：熔断时间过后进入半开状态，允许少量请求试探。若试探请求成功（通过限流检查且执行正常），则恢复 CLOSED；若试探再次触发限流或执行异常，则回到 OPEN 并重置熔断时间（指数退避，最大 600 秒）。

状态转换通过 Redis 存储（key: `circuit_breaker:{task_id}:state`）实现分布式协调。每次检查熔断时读取状态，修改状态时使用 Lua 脚本保证原子性。

**Lua 脚本示例**：

```lua
-- 熔断器半开试探后决定是否恢复
local key = KEYS[1]
local state = redis.call('GET', key)
if state == 'half_open' then
    local success = tonumber(ARGV[1])  -- 1: 试探成功, 0: 试探失败
    if success == 1 then
        redis.call('SET', key, 'closed')
        redis.call('EXPIRE', key, 3600)  -- 重置过期时间
        return 1  -- 恢复
    else
        local retry_after = tonumber(redis.call('GET', key .. ':retry_after'))
        redis.call('SET', key, 'open')
        redis.call('EXPIRE', key, retry_after * 2)  -- 指数退避
        redis.call('SET', key .. ':retry_after', retry_after * 2)
        return 2  -- 继续熔断
    end
end
return 0
```

### 5.2 验证情况

**场景 1：正常调度压力测试**

- 对 1 个任务在 1 秒内发送 100 个请求（参数不同）。
- 预期：前 10 个通过（窗口 60s 内 max=10），后续 90 个被限流。
- 实际：通过了 12 个（令牌桶突发容忍），剩余 88 个被限流。符合预期。

**场景 2：完全重复请求**

- 对同一参数请求 5 次。
- 预期：第 1 次通过，后 4 次去重拒绝。
- 实际：4 次去重命中，无任务执行。

**场景 3：熔断测试（灰度集群）**

- 通过控制台向一个任务连续发送失败请求（让调度器模拟下游超时），触发限流告警，当失败率 > 20% 后熔断器进入 OPEN 状态 120s。
- 观察期内所有该任务的调度请求被直接拒绝，120s 后进入 HALF-OPEN，发送一个试探请求成功，熔断恢复。
- 实际熔断持续时间略有偏差（±3s），可接受。

## 6. 已知限制与注意事项

### 6.1 限制

1. **去重键精度问题**：`parameters_md5` 对参数顺序敏感，若客户端发送的参数 JSON 键顺序不一致，会导致不同的去重键，无法正确去重。已在客户端 SDK 强制 `sort_keys=True` 序列化，但历史版本可能仍存在问题。
2. **滑动窗口分布式一致性**：当前使用 Redis 单实例存储窗口数据，若 Redis 故障切换期间丢失数据，可能导致限流规则短暂失效（窗口重置）。计划引入 Redis Cluster 或使用 Redlock 优化。
3. **熔断器误触发风险**：当大规模故障导致所有任务被限流时，熔断器可能进入 OPEN 使问题加剧。目前通过 `HALF-OPEN` 试探和指数退避减轻此风险，但需关注整体指标。
