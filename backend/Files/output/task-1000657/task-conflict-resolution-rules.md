## 1. 背景与目标  

### 1.1 问题来源  
在多任务调度系统、CRM（客户关系管理）、OA（办公自动化）或工单管理平台中，同一用户可能同时被分配或主动创建多个任务。若不加以约束，任务可能因资源竞争、时间重叠或状态互斥而产生冲突，导致执行混乱、数据不一致或系统异常。例如：  
- 一名客服在同一时间被指派处理两个客户的投诉电话。  
- 一名开发人员同时被安排参加两个线上会议。  
- 一个运维工具对同一服务器同时执行重启和备份任务。  

### 1.2 核心目标  
本规则旨在明确**同一用户**（自然人、系统账号或自动化代理）在不同任务之间**不产生冲突**的判定标准与处理逻辑，确保：  
1. 任务按合理顺序执行，避免并行冲突。  
2. 高优先级任务可打断低优先级任务。  
3. 同类型任务串行化。  
4. 提供可自动或半自动执行的冲突解决路径。  

### 1.3 适用场景与用户身份  
- **用户身份**：  
  - 自然人（如员工、客服、技术员）  
  - 系统服务账号（如调度器、自动化脚本、API消费者）  
  - 虚拟资源代理人（如机器人、AI助理）  
- **适用场景**：  
  - 任务分配系统（如Jira、工单系统）  
  - 日历与日程管理（如Outlook、Google Calendar）  
  - 资源调度平台（如Kubernetes、分布式任务队列）  
  - 权限审批流（如同一审批人同时处理多个审批）

## 2. 冲突定义  

### 2.1 任务冲突的判定维度  
若同一用户的两个任务（或一个任务与自身）在以下任一维度上产生交集，则视为冲突：  

| 冲突类型 | 定义 | 示例 |  
|----------|------|------|  
| **时间重叠** | 两个任务的时间窗口（开始时间~结束时间）存在非零重叠间隙，且用户无法同时处理。 | 任务A: 09:00-10:00 会议；任务B: 09:30-10:30 会议。 |  
| **资源独占** | 任务需要独占某类资源（如特定设备、网络端口、数据库锁），而另一任务也需要同一资源。 | 任务A: 使用打印机；任务B: 同一时段使用同一打印机。 |  
| **状态互斥** | 任务对用户或关联对象的状态要求互斥（如：“空闲” vs “忙碌”、“未开始” vs “进行中”）。 | 任务A 要求用户状态为“在线”；任务B 要求用户挂起（脱机）。 |  
| **类型互斥** | 同一类型任务必须串行执行，不可并行（如：两个“审核”任务不能同时处理）。 | 同一审批者同时打开两个审批单。 |  

### 2.2 冲突判定的粒度  
- **精细粒度**：按任务时间、资源、状态的交集精确计算。  
- **粗粒度**：仅根据用户“忙碌”时段阻挡新任务分配（忽略资源细节）。  
- 本规则采用**双模式**：系统默认使用粗粒度，当检测到资源或类型标志时，自动切换精细粒度。

## 3. 规则集  

### 3.1 核心规则一览  

| 规则编号 | 规则名称 | 描述 | 优先级 | 默认开关 |  
|----------|----------|------|--------|----------|  
| R1 | 时间串行 | 同一用户的任务默认按**开始时间**升序顺次执行，不允许时间窗口重叠（除非用户显式声明可并行）。 | 最高 | 开 |  
| R2 | 优先级抢占 | 高优先级任务（P1）可以抢占低优先级任务（P3）的时间段，原任务被推迟或重新安排。 | 高 | 开 |  
| R3 | 同类型串行 | 同一类型的任务（如“维修”、“审批”、“呼叫”）必须串行执行，即使时间不重叠也不允许同时处理。 | 中 | 关（需业务配置） |  
| R4 | 资源互斥 | 若任务标记了独占资源，则冲突判定需检查资源占用；否则忽略。 | 中 | 开 |  
| R5 | 状态兼容 | 任务不能设置与用户当前状态相矛盾的要求（如要求“空闲”时用户已处于“忙碌”）。 | 中 | 开 |  
| R6 | 可自愿覆盖 | 用户或管理员可手动解除冲突（如“我接受同时处理”），但需记录操作日志。 | 低 | 关 |  

### 3.2 规则详细说明  

#### R1 时间串行  
- **触发条件**：系统尝试将新任务分配给用户，或用户创建新任务时。  
- **处理逻辑**：  
  1. 检查新任务的时间段（start, end）是否与用户现有任务的时间段重叠。  
  2. 若重叠，根据冲突处理流程（见第4章）选择方案：排队、调整或拒绝。  
- **例外情况**：  
  - 任务标记为`allow_overlap=true`（如“可同时参加多个会议”的任务）。  
  - 用户优先级配置为“允许并行”。  

#### R2 优先级抢占  
- **触发条件**：新任务的优先级高于现有任务的优先级，且时间重叠。  
- **处理逻辑**：  
  1. 低优先级任务被标记为“被抢占”，其状态变为“暂停-等待资源”。  
  2. 低优先级任务的剩余部分重新放入队列，尝试在其他时间段执行。  
  3. 若低优先级任务已开始执行，需根据其原子性决定是否中断（可中断的任务提供`interruptible=true`标志）。  
- **例外情况**：  
  - 若低优先级任务已被用户锁定（locked=true），则不可抢占。  
  - 抢占操作需通知用户。  

#### R3 同类型串行  
- **触发条件**：新任务与现有任务属于同一任务类型（type字段相同），且用户未选择“并行处理该类型”。  
- **处理逻辑**：  
  1. 新任务必须等待现有同类型任务完成后才能开始。  
  2. 即使时间不重叠，若用户目前持有任何同类型未完成任务，新任务也需排队。  
- **例外情况**：  
  - 若任务类型为`concurrent_allowed=true`，则允许并行。  
  - 用户可通过配置关闭此规则（但需管理员授权）。  

#### R4 资源互斥  
- **触发条件**：两个任务均声明了相同的独占资源ID（如`resource_id: printer-01`）。  
- **处理逻辑**：  
  1. 资源按“先占先得”原则加锁。  
  2. 后续任务需等待资源释放或尝试其他资源。  
  3. 若资源可共享（`shareable=true`），则不视为冲突。  

#### R5 状态兼容  
- **触发条件**：任务要求用户状态为特定值（如`required_user_status: "idle"`）。  
- **处理逻辑**：  
  1. 读取用户当前状态（来自用户状态表）。  
  2. 若不符合要求，则冲突。系统可尝试自动调整用户状态（如设为忙碌），或拒绝任务。  
- **例外情况**：用户可以通过临时授权覆盖。  

#### R6 可自愿覆盖  
- **触发条件**：用户主动选择“接受冲突”。  
- **处理逻辑**：  
  1. 系统记录覆盖操作（who, when, reason）。  
  2. 任务照常执行，但需承担可能的风险（如超时或失败）。

## 4. 处理流程  

### 4.1 通用冲突检测流程（伪代码）  

```
function detectConflict(userId, newTask):
    conflicts = []
    for each existingTask in getUserTasks(userId):
        if timeOverlap(newTask, existingTask):
            conflicts.append(new Conflict(existingTask, "TIME"))
        if resourceConflicts(newTask, existingTask):
            conflicts.append(new Conflict(existingTask, "RESOURCE"))
        if typeConflicts(newTask, existingTask):
            conflicts.append(new Conflict(existingTask, "TYPE"))
        if statusConflicts(newTask, existingTask):
            conflicts.append(new Conflict(existingTask, "STATUS"))
    return conflicts
```

### 4.2 冲突解决流程（按优先级）  

1. **检测冲突** → 列出所有冲突。  
2. **应用用户偏好** → 若用户已配置“允许并行”，则直接通过（但记录日志）。  
3. **应用规则覆盖** → 若用户主动点击“强制创建”，则通过。  
4. **自动处理**：  
   - 若有抢占（R2），执行抢占流程。  
   - 否则，若可排队（时间串行），计算最近可用时间槽并建议调整。  
   - 否则，拒绝任务并返回冲突详情。  
5. **通知** → 通过邮件、站内信或WebSocket推送冲突通知给用户。  
6. **用户确认** → 用户可在24小时内回复确认或修改。超时则系统自动执行默认处理（通常为拒绝或排队）。  

### 4.3 处理策略对比  

| 策略 | 描述 | 适用场景 |  
|------|------|----------|  
| **排队** | 将新任务插入用户任务队列末尾，自动重新计算开始时间。 | 低优先级任务、时间不紧迫。 |  
| **动态调整** | 自动调整任务时间（如缩短时长、延后开始）以消除冲突。 | 任务可调整（`adjustable=true`）。 |  
| **抢占** | 高优先级任务打断低优先级任务。 | 紧急且低优先级任务可中断。 |  
| **拒绝** | 直接返回冲突错误，由上游任务分配器处理。 | 任务不可调整且无抢占资格。 |  
| **人工干预** | 生成工单或通知管理员协调。 | 自动化无法解决的复杂冲突。 |

## 5. 示例说明  

### 示例1：时间重叠且无抢占（默认排队）  
**场景**：用户张三已有任务A（10:00-11:00 客户回访），系统尝试分配任务B（10:30-11:30 方案评审）。  
**规则应用**：  
- 时间重叠 → 冲突（R1）  
- 任务A优先级P3，任务B优先级P3，无抢占（R2不触发）  
- 任务类型不同（回访 vs 评审），R3不触发  
- 无资源标志 → R4不触发  
- 用户状态兼容 → R5通过  

**处理流程**：  
1. 系统检测到时间冲突。  
2. 计算用户下一个空闲时段（11:00后）。  
3. 建议将任务B调整为11:00-12:00，同时通知张三。  
4. 张三确认调整。  
**结果**：任务B安排在11:00-12:00执行。  

### 示例2：优先级抢占（高优先级打断低优先级）  
**场景**：用户李四正在执行任务C（15:00-16:00 日常巡检，P5），系统创建紧急任务D（15:15-15:45 修复生产故障，P1）。  
**规则应用**：  
- 时间重叠 → 冲突（R1）  
- 任务D优先级P1 > 任务C优先级P5 → 触发R2抢占  
- 任务C可中断（`interruptible=true`）  

**处理流程**：  
1. 系统暂停任务C（标记为“被抢占”）。  
2. 任务D立即开始。  
3. 任务D完成后，系统将任务C剩余部分（15:45-16:00）重新入队，并通知李四。  
**结果**：生产故障优先修复，日常巡检延后完成。  

### 示例3：同类型串行（人工审核场景）  
**场景**：审批人王五同时收到两个订单审批任务（类型=“order_approval”），任务E（14:00-14:15）和任务F（14:20-14:35）。  
**规则应用**：  
- 时间无重叠 → R1通过  
- 但类型相同 → R3触发（同类型串行开启）  
- 因为用户正在处理任务E，任务F不能同时打开  

**处理流程**：  
1. 系统检测到任务F与任务E同类型。  
2. 任务F加入等待队列，状态变为“等待-同类型互斥”。  
3. 任务E完成后，系统自动激活任务F。  
**结果**：审批人按顺序处理，不会同时打开两个审批界面。

## 6. 附录  

### 6.1 术语表  

| 术语 | 定义 |  
|------|------|  
| 任务 | 分配给用户或由用户创建的一个可执行工作单元，包含开始时间、结束时间、优先级、类型、资源要求等。 |  
| 用户 | 执行任务的实体，可以是人、服务账号或机器人。 |  
| 时间重叠 | 两个任务的时间段 [start, end) 存在交集。 |  
| 优先级 | 任务的重要程度，通常分为P0~P5（P0最高）。 |  
| 抢占 | 高优先级任务强制暂停低优先级任务并占用其时间段的行为。 |  
| 可中断 | 任务支持在执行过程中被暂停（保存状态）的属性。 |  
| 独占资源 | 一次只能被一个任务使用的资源（如物理设备、网络端口）。 |  
| 任务类型 | 任务的功能分类（如“审批”、“维修”、“会议”）。 |  
| 同类型串行 | 同一任务类型的多个任务必须顺序执行，不可并行。 |  
| 状态兼容 | 任务对用户当前状态（空闲/忙碌/离线）的要求是否匹配。 |  
| 排队 | 将任务放入待处理队列，等待前序任务完成后自动执行。 |
