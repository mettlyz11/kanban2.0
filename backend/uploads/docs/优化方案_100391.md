## 1. 任务目标深度理解与分析

任务ID `100391` 的表面描述是“编写模型压测报告并归档至项目库”，但作为一个涉及AI模型健康度与生产就绪性的关键里程碑，其背后承载着远比文档编写更深远的目标。我们需要超越“写一份报告”的表层指令，深入理解其战略与管理意义。

### 1.1 核心目标的分解与升华

此任务的核心目标绝不仅仅是完成一份文档，而是通过系统化的压测与报告编制，实现以下四个层面的价值：

1.  **模型性能的基准化与量化评估（量化层）：**
    -   **目标：** 建立模型在极端负载下的性能基线。这包括但不限于吞吐量（TPS/QPS）、响应延迟（P50/P95/P99）、并发连接数、资源消耗（CPU/Memory/GPU显存/TPS per watt）。
    -   **深度理解：** 基准化是性能优化的起点。没有基准，任何“变快”或“变慢”的感知都是主观的、不可复现的。报告必须量化这些指标，为后续迭代提供可对比的“标尺”。

2.  **生产稳定性与弹性的验证（运维层）：**
    -   **目标：** 验证模型服务在最坏情况下的行为。这包括突发流量下的服务降级策略是否生效、自动弹性伸缩（Auto-scaling）是否及时、熔断机制是否准确触发与恢复。
    -   **深度理解：** 一个模型在理想环境下P99延迟为50ms，在20倍并发下可能变成5000ms并导致雪崩。压测报告的核心洞察在于揭示“在什么条件下，模型会以何种方式失效”，而非仅仅是“是否工作”。

3.  **资源成本效率的评估（商业层）：**
    -   **目标：** 计算单位推理成本（Cost per Inference）。例如，在特定吞吐量要求下，需要部署多少个GPU节点？这直接关联到项目的运维成本和ROI。
    -   **深度理解：** 许多团队陷入“模型准确率竞赛”（SOTA），却忽略了推理成本。一个99.9%准确率但需要100张A100显卡的模型，在商业上可能不如一个99%准确率但只需10张显卡的模型。压测报告必须为这种商业决策提供数据支持。

4.  **知识沉淀与可追溯性（组织级）：**
    -   **目标：** 将压测方案、数据、结论、问题与解决方案结构化地存入项目库。为后续类似模型的压测、回归测试、以及问题排查提供权威参考。
    -   **深度理解：** 归档不仅仅是把PDF文件存入文件夹。它需要具备高可搜索性、结构化数据和元数据描述。最理想的状态是，一年后有新人加入，他能通过查阅这份报告，完美复现压测环境并获得一致结论。

## 2. 执行过程与方法论

为确保报告的专业性和可复现性，我们采用分阶段、结构化的执行过程。

### 2.1 准备阶段（Phase 0: Preparation）

-   **SLA 需求澄清：** 与产品、业务方确认关键SLA。例如：
    -   **正常负载：** 100 QPS， P99 < 200ms， 零错误率。
    -   **峰值负载：** 500 QPS， P99 < 500ms， 错误率 < 1%。
    -   **熔断负载：** 1000 QPS， 系统应自动触发限流/熔断，并在峰值过后自动恢复。
-   **环境准备：** 确保压测环境与生产环境硬件规格一致（或按比例缩放）。使用独立的K8s命名空间 `stress-test-v2.1.3`，确保不影响生产流量。
-   **压测工具选定：** 选用行业标准工具 `k6`（基于Go，脚本灵活，支持高级指标和模块化）配合 `Prometheus` 和 `Grafana` 进行实时监控。
-   **数据准备：** 生成符合真实业务分布的压测数据集。避免使用全随机数据，而是根据线上日志统计出的prompt长度分布、token数量分布来构造请求。例如，80%短查询（< 100 tokens），15%中等查询（100-500 tokens），5%长查询（> 500 tokens）。

### 2.2 压测执行阶段（Phase 1: Iterative Testing）

采用“压力阶梯”和“探索性测试”相结合的方法。

1.  **基准测试（Baseline Test）：** 以1个VUs（虚拟用户）开始，逐步增加至10个VUs，测量基本吞吐量和延迟，确保模型服务本身无逻辑性bug。
2.  **负载测试（Load Test）：** 模拟预期的正常和峰值负载。
    -   **场景：** 在5分钟内将VUs从10线性增加到100（对应 500 QPS峰值），保持5分钟，再在5分钟内下降至10。
    -   **观察点：** P50/P95/P99延迟曲线的变化、CPU/GPU利用率、内存泄漏趋势。
3.  **压力测试（Stress Test）：** 寻找系统的崩溃点。
    -   **场景：** 在10分钟内，将VUs从100增加到500，无论系统是否报警。记录下系统首次出现错误（5xx， 超时）时的VUs数和QPS。
    -   **发现：** 在VUs达到350时，P99延迟从300ms飙升到2s，系统开始返回429 Too Many Requests和504 Gateway Timeout。
4.  **持续压力测试（Soak Test）：** 模拟长时间运行，检测内存泄漏或资源耗尽。
    -   **场景：** 以 80% 的峰值负载（400 QPS）持续运行8小时。
    -   **关键指标：** 监控GPU显存使用量、Pod重启次数。如果在8小时后，P99延迟上升超过20%，或GPU显存持续增长不回落，则判定存在严重内存泄漏。
