**2.1.2 API功能模块梳理**
假设本次待测试的API是一个**社交平台的用户画像分析API（User Profile Analytics API）**。我们将它拆解为以下核心功能模块：
1.  **用户基础信息查询：** `GET /v1/users/{user_id}`
2.  **用户活动时间线检索：** `GET /v1/users/{user_id}/timeline?from=<timestamp>&to=<timestamp>`

**示例片段（Python）：**

```python
import requests
import time
# ... (省略)

def get_user_profile_with_retry(user_id, access_token, max_retries=3):
    retries = 0
    while retries < max_retries:
        response = requests.get(
            f"{BASE_URL}/users/{user_id}",
            headers={"Authorization": f"Bearer {access_token}"}
        )
        if response.status_code == 200:
            return response.json()
        elif response.status_code == 429:  # Rate Limit
            wait_time = int(response.headers.get("Retry-After", 2 ** retries))
            print(f"Rate limited, retrying in {wait_time}s...")
            time.sleep(wait_time)
            retries += 1
        elif response.status_code >= 500:
            print(f"Server error: {response.status_code}. Retrying...")
            time.sleep(2 ** retries)
            retries += 1
        else:
            response.raise_for_status()
    raise Exception(f"Failed to get user after {max_retries} retries.")
```

**2.2.2 测试用例设计方法论**
采用**等价类划分**、**边界值分析**和**正交实验法**。
*   **功能测试 (Positive/Negative):**

    *   **负向:**
        *   **认证失败:** 无Token、过期Token、无效Token (预期401)。
        *   **授权不足:** 使用低权限Token访问高权限API (预期403)。
        *   **资源不存在:** 请求一个不存在的用户ID (预期404)。
        *   **参数校验:** 无效的日期格式、负数page_size、超出范围的limit (预期400)。
*   **性能与压力测试:**
    *   **基准测试:** 单用户、单线程下，接口的平均延迟、P50、P99延迟。
    *   **负载测试:** 模拟10、50、100、500个并发用户，持续5分钟，观察系统响应时间和错误率。

## 3. 核心发现和洞察（至少5点）

基于上述执行过程，我们针对“用户画像分析API”提出了以下核心发现：

### 洞察一：并发瓶颈点在于“批量聚合”接口，而非“单用户查询”接口
*   **数据支撑：** 在100并发用户下，`GET /v1/users/{user_id}` 的P99延迟稳定在200ms，而 `POST /v1/users/batch` 的P99延迟飙升到8秒，错误率高达12%。
*   **根因分析：** 批量接口采用了 `select * from users where id in (?)` 的非预编译SQL查询，且未使用连接池。由于没有做批量化处理，每次请求都会打开一个新的数据库连接。高并发下，DB连接池被快速耗尽，请求排队，导致响应时间急剧增加，部分请求超时。
*   **结论：** API性能优化的优先级应聚焦于**优化批量接口的数据处理逻辑**，而非单点查询。

### 洞察二：错误处理策略不统一，外部开发者体验差
*   **数据支撑：** 在测试400错误（参数校验）时，发现不同接口返回的错误码格式不一致。例如，`GET /v1/users` 返回 `{"error": "invalid_param", "detail": "..."}`，而 `POST /v1/users/tags` 返回 `{"status": "error", "msg": "..."}`。
*   **结论：** 缺乏统一的**错误响应标准**（如 RFC 7807 Problem Details）。这使得客户端开发者无法编写统一的错误处理逻辑，必须为每个接口单独适配，极大地增加了集成成本。这是典型的“内部实现逻辑”泄露到外部API接口的表现。

### 洞察三：鉴权系统的“临时性”Token有效期过短，缺乏Refresh Token机制
*   **数据支撑：** 测试脚本在运行1小时后，超过60%的请求失败，错误码均为401。
*   **根因分析：** 当前API Token有效期为30分钟，且未提供Refresh Token。这意味着任何长时间运行的应用（如后台数据分析脚本、移动端后台同步）都必须每30分钟让用户重新登录，用户体验极差。
*   **结论：** 必须引入OAuth 2.0标准中的**Refresh Token**机制，允许应用在用户离线状态下，默默地获取新的Access Token，从而实现无缝的长时间会话。

### 洞察四：异步任务（`POST /v1/users/tags`）缺乏明确的状态查询和超时机制
*   **数据支撑：** 调用该接口后立即返回 `202 Accepted` 和一个 `task_id`。但测试中发现，对于同一个 `task_id`，状态轮询接口 `GET /v1/tasks/{task_id}` 在5分钟后仍可能返回 `processing`，且没有明确的“最大等待时间”。
*   **结论：** 接口缺乏**任务超时和失败通知**机制。一个长时间卡住的异步任务会消耗服务端资源。应增加任务的最大执行时间（例如10分钟），超时后自动标记为 `failed`，并返回错误原因。同时，应支持 Webhook 回调，在任务完成或失败时主动通知客户端。

### 洞察五：性能测试暴露了内存泄漏隐患
*   **数据支撑：** 在稳定性测试中，我们运行了12小时的匀速流量（20并发/秒）。服务器的内存使用在最初2小时稳定在2GB，但随后以每小时约150MB的速度线性增长，至第12小时时已达到3.8GB，接近上限。
*   **根因分析：** 经过GC分析（使用 `pprof` 工具），发现 `POST /v1/users/batch` 接口在处理完请求后，存在一个 `HashMap` 未被释放，用于缓存一些中间结果。这个缓存设置了上限（如10万个对象），但缓存对象的key是用户输入，没有被正确清理，导致缓存随着时间推移无限膨胀。
*   **结论：** API存在明显的**内存泄漏**问题。在投入生产前必须修复，否则长期运行将导致服务OOM（Out Of Memory）
