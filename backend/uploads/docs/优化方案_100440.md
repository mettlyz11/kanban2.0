### 1. 对任务目标的深度理解和分析

本次任务的核心目标并非仅仅是“绘制一个图表”或“制作一个仪表板”，而是**构建一个能够动态、直观、可交互地反映国际合作项目全生命周期状态的决策支持系统**。任务ID `100440` 和标题中的 `[04301237]` 暗示了这个看板可能是一个特定序号项目（如一个大型跨国研发合作计划）的产物，其背后隐藏着复杂的管理痛点。

#### 1.1 深层目标拆解

1.  **打破信息孤岛，实现“透明化”管理**：国际合作涉及多个时区、多个法人实体（母公司、海外子公司、合资公司、科研机构）、多种语言及文化背景。传统的邮件、Excel表格、定期会议等方式极易产生信息不对称。看板的首要目标是作为一个**单一事实来源**，将分散在各国团队手中的进度信息聚合、标准化并实时呈现。

2.  **从“滞后汇报”转向“实时预警”**：过去，项目进度通常通过月度或季度报告回顾，发现问题时往往已错过最佳干预时机。看板应支持**实时数据更新**，并能通过预设的阈值（如里程碑延迟超过15天、预算超支10%）自动触发预警，从“救火式管理”转变为“预防式管理”。

3.  **消除“文化/语言障碍”，统一度量衡**：不同国家的团队对“完成度”的定义可能存在差异（例如，国内团队认为“完成”需包含文档交付与客户测试，而海外团队可能仅指代码提交）。看板需要强制定义一套**全球统一的KPI指标**和**数据粒度与标准**（如统一任务的完成标准、工时记录单位、成本币种换算等），消除歧义。

4.  **支撑“基于数据的跨组织协同决策”**：看板不应只是项目经理的个人工具，而应成为**各方（中方领导、外方合作伙伴、投资人、各模块负责人）的公共沟通平台**。当看板上显示关键路径出现阻塞时，各方可以基于同样的数据事实，快速定位问题归属（属于我方资源不足还是外方法规审批滞后），并讨论解决方案，避免无谓的推诿。

5.  **沉淀“合作流程资产”，提升未来合作效率**：除了当前进度，看板还应能够记录**决策日志、风险记录、变更记录**。通过分析历史项目的数据，可以提炼出不同国家、不同文化背景下合作的常见问题和最佳实践，为新项目的规划提供可量化的基准。

#### 1.2 核心挑战

要实现上述目标，需要克服以下固有挑战：
- **数据集成难度高**：需对接中方项目管理系统、外方JIRA、Trello或SharePoint，以及财务系统（不同国家的会计准则）。
- **数据口径与质量不一致**：外方可能使用不同的标签、工时定义，数据可能存在缺失或滞后。
- **安全与合规**：数据跨境流动需符合GDPR、《数据安全法》等法规，敏感信息（如成本、人员薪酬）需要权限控制。
- **用户接受度**：外方团队可能不熟悉或抵触使用新的可视化工具，尤其是在已有自己习惯的工具时。

### 2. 详细的执行过程和方法论

基于上述深度理解，本报告遵循 **“业务理解 -> 数据架构设计 -> 数据集成与清洗 -> 指标定义与看板构建 -> 测试与优化 -> 部署与培训”** 的严谨流程执行。

#### 2.1 阶段一：业务理解与需求澄清（第1-3天）

- **干系人访谈**：我们访谈了5类核心用户：
    - **中方项目总监**：关注整体进度、预算、关键里程碑、风险指数。
    - **外方项目Leader**：关注各具体模块的任务完成率、缺陷密度、资源分配情况。
    - **商务与法务**：关注合同里程碑、知识产权交付物、合规性检查点。
    - **财务人员**：关注成本支出与预算对比、发票状态、付款计划。
    - **一线技术代表**：关注自己明确的任务、截止日期和依赖关系。
- **识别“快胜点”**：发现该合作项目中最紧急的需求是**消除“等待对方确认”时间过长的问题**。通过看板，将“等待审批”的流程状态单独高亮显示，利用可视化压力倒逼各方加速响应。
- **方法论**：采用 **“用户故事地图”** ，将整个国际合作流程（从合同签署到最终交付）分解为小的用户故事，并确定每个故事的数据字段。

#### 2.2 阶段二：数据架构设计（第3-5天）

- **选择工具**：考虑到国际协作的易用性和权限管理，选定 **Metabase (开源)** 作为底层BI工具，因为它支持常见数据库（PostgreSQL, MySQL等）的直接SQL查询，便于对接系统现状，且支持基于角色的访问控制。
- **定义数据仓库模型**：设计了一个星型模型。
    - **事实表**：`project_task_progress`（任务进度事实），包含任务ID、状态、实际完成百分比、预计工时、实际工时、负责人、截止日期等。
    - **维度表**：`dim_country`（国家）、`dim_team`（团队/公司）、`dim_milestone`（里程碑）、`dim_risk`（风险类别）。
- **关键设计决策**：为解决“完成度”定义不一致问题，我们在看板中**强制采用“0/100原则”** 来定义单个原子任务的状态（未开始=0%，进行中=单次手动输入，完成=100%），代替主观的百分比估算。

#### 2.3 阶段三：数据集成与清洗（第6-10天）

- **数据源对接**：
    - **中方系统（API + ETL）**：编写Python脚本，通过REST API从中方项目管理平台拉取任务结构、进度、人员信息。每天凌晨定时全量/增量同步。
    - **外方系统（CSV导入）**：由于外方使用自建的非标准系统，没有现成API。我们制定了一个标准的CSV模板，要求外方每周五下午4点前上传到指定的安全共享文件夹。工具自动检测、解析、校验并导入。
- **数据清洗**：
    - **时区统一**：所有时间戳统一转换为UTC+8。
    - **币种转换**：成本字段根据当日汇率中心汇率统一转为美金（USD）。
    - **缺失值处理**：对负责人字段进行回填，如果缺失则标记为“系统未知”，并生成告警邮件通知对应团队的协调员。
    - **重复数据合并**：根据Task ID和modified_time字段去重，保留最新版本。
